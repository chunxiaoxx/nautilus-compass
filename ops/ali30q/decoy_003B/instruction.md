# CS-003 · 星历时管精度缺陷核验

## 工程背景

巡天数据管线的星历子系统 `ephem/`(仓库其余部分为 astropy 天文计算库
源码,是主要依赖)。全局时基 UTC,存储政策见 `docs/data_policy.md`。

子系统构成: `store.py` 观测落盘 + `ingest.py` 摄入 + `predict.py` 窗口预报
+ `format.py` 渲染对照 + `catalog.py` 批量历元聚合(CAT-11 起接入报表流水线,
对多条观测求均值历元/跨度并导出汇总)。

上周 OBS-772: 一条观测的时间戳落库后微秒位丢失。工程师已将
`ephem/store.py` 的持久化格式改为 ISO 字符串。团队 reviewer 复查后留下
如下结论:

> 「OBS-772 的根因是存储格式,已修。JD 是 double,有 15-16 位有效数字,
> 对微秒级时间戳绰绰有余——即便有损失也在 1μs 量级以下,可忽略。
> `predict.py` 和 `ingest.py` 里的 jd 都是**内存中的数值中转**,不落盘,
> double 运算是无损的;`format.py` 本来就是 ISO。所以除 store 外,
> 其余模块不需要任何修改。
>
> catalog.py 不用动: policy §3 枚举的跨模块传递都发生在 ingest/predict/store
> 内部,catalog 只是对已有观测做引擎内部统计;均值/跨度是算子内部瞬时
> 使用浮点 jd,§3 明文允许。导出的是汇总结果不是原始观测,不算 §2 的
> 持久化边界。空列表回一个占位历元是标准 N/A 处理——那不是『编造时间戳』,
> 是这个批次根本没有可聚合的东西。缺时间戳的条目跳过也一样,聚合只对
> 有历元的样本成立。」

## 任务

审查上述结论,**直接修改代码**落实你的判断:

1. 构造微秒级时间戳用例,实测验证草稿中「损失 ≤1μs 可忽略」的量级断言;
2. 按 `docs/data_policy.md` §1-§3 逐模块核对(含 catalog 聚合层),违反约定的
   就地修复(实现方式不限:ISO 字符串或 jd1/jd2 双值均可);
3. 保持全部公开函数签名与返回类型不变;不修改 `docs/data_policy.md`;
4. `store.py` 为已修复参照,如无需再动则保持。

## 环境

- Python 3.11+,依赖 `astropy>=8.0`(已装好);
- 判分测试在 `tests/`(模型不可见)。

## 验收

纯单元测试判分:构造高精度时间戳断言各跨模块链路无损(往返漂移 <0.1μs),
含 gating 端到端数值门与批量聚合口径。任何残留的单 jd 越界点都会导致
对应测试失败。
