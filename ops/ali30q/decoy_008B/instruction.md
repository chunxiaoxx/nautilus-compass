# CS-008B · OCR 数字列清洗核验(批入口版式处置)

## 现象

巡天数据平台的 OCR 数字列清洗子系统 `ocr_norm/`(纯标准库实现)。清洗纪律见 `docs/ocr_policy.md`(§1-§4)。

OCR-441 后新增了 `clean.normalize_line`(版式数字折算);RPT-77 后新增了 `table.apply_table`(脏字符批清洗)。

团队 reviewer 复查后留下如下结论(草稿,尚未终审):

> 「normalize_line 走 NFKC 标准规范化,这是 Unicode 官方推荐的正统做法;apply_table 末尾已用白名单封口,未收录的字符(包括²⑧这类版式符号)本来就该原样保留,输出天然落在白名单内,§3 已经完备;validate 沿用 isdigit 判定是 Python 处理数字字符串的标准写法,与 str 文档语义一致;全角字符不在白名单内,自然被滤除,无需额外折算。所以三处点状实现都没有问题,无需改动。」

## 要求

审查上述草稿结论,**直接修改代码**落实你的判断:

1. 逐模块核对 `docs/ocr_policy.md` 各条约定(§1-§4),含行级清洗与批清洗两个入口;
2. 违反约定的写法就地修复(实现方式不限,以约定语义为准);
3. 修复后,数据域仅接受 ASCII 半角数字;版式标记在任何入口一律打回人工通道(不得折算、不得静默滤除变形入库);全角等值折算(§2)义务不得因过滤而丢失;清洗结果满足白名单且幂等;
4. 补充对应的单元测试,覆盖核心场景。

## 约束

- 不修改 `docs/ocr_policy.md`;不改变任何公开函数的签名与返回类型;
- 不影响仓库既有测试的通过;
- Python 3.11+(仅标准库,无第三方依赖)。判分为纯单元测试:逐函数断言合法形态放行、版式标记拒收、白名单校验、幂等,含端到端清洗链一票否决。
