# 飞书多维表格做 FDE 运营控制台 · 自建设计(2026-06-12 · 4 路并行调研落成)

> 用户要求:别照搬模板,先全面学多维表格(看板/agent接入/工作流)再自己建。本 doc = 调研结论 + 我们自己的控制台架构 + API自动建/UI手点 分工 + 桥升级路径。
> 调研源:官方 open.feishu.cn 服务端文档 + feishu.cn 帮助中心(4 agent 并行·全文带 URL 见 session memory)。

## 0. 一句话架构(surface 解耦的兑现)
**飞书多维表格 = 操作台/数据面(人看人操作)· 我们引擎 = 权威逻辑(派单/判分/verdict·system-of-record)· 桥 = 事件驱动 + Bitable Server API。** 飞书怎么换模板/视图都行,只要桥的列契约对齐,引擎不动。🔴 判分/派单逻辑绝不搬进飞书自动化(配额 200/月会爆 + 分叉第二套真相)。

## 1. 调研关键事实(决定方案的硬约束)

### A. 能 API 全自动建的(我来)
- 表、字段(文本/数字/单选/多选/日期/复选/人员/电话/url/附件/**双向关联(21)/单向关联(18)**/自动编号/创建修改时间人)
- 记录批量读写(batch **≤1000/请求·全成全败**)、表单视图、看板视图**空壳**、过滤(filter_info)、隐藏字段
- **高级权限角色 app_role / 协作者 app_role_member 可 API CRUD**(招新专家可程序化授权)

### B. 必须人在 UI 点一次的(API 做不了 or 静默 no-op)
1. 🔴 **看板分组字段**(实测:patch group_conditions 返 code=0 但 property=null = 假成功)→ 看板壳 API 建,分组列拖一次
2. 🔴 **Lookup(19)/ Rollup 统计** → 专家"承接数/通过率"汇总列必须 UI 配
3. ⚠️ **公式表达式**(字段壳可建·公式内容 UI 写)
4. 🔴 **按钮/AI 字段/Stage 流程字段**
5. 🔴 **仪表盘** = API 仅 list/copy 无 create → UI 搭 或 做模板 base 用 copy 克隆
6. 🔴 **自动化工作流** = 无 API,UI 配一次(配完 webhook URL 后可纯 HTTP 驱动)

### C. 架构级发现(改变方案)
- **事件驱动 > 轮询**:长连接事件订阅 `drive.file.bitable_record_changed_v1` → 专家改状态即 push 到我方 agent(替当前 5min 轮询·省配额·实时)。约束:3s 内处理 / 每应用 ≤50 连接 / 须先订阅表 / 公式字段不触发。
- **飞书自动化能当桥的飞书→引擎那半**:字段变更→「发送 HTTP 请求」动作 POST 到引擎端点。但 **自动化运行 200 次/月(免费)→ 高频不放飞书**,只做低频通知;高频拉取留我方 poller/Server API。
- **AI 字段=内部轻量辅助**(格式自检/摘要/粗分类/疑似AI检测)**不做权威判分·不生成交付内容**(守买方红线)。权威判分留 soul-scorer harness;若要 agent 在表内直接判,走「AI Agent 节点 + 自定义 MCP」包 harness(后续选项)。
- **关联/lookup/rollup 不跨 base** → 要互相汇总的表必须**同 base**。
- 🔴 **买方机密必须独立 base 物理隔离**(高级权限是逻辑隔离·管理员可绕过·不足以保密)= 宪章 §E 红线。
- **限流**:多维表格**不可提频**(429/99991400·按 x-ogw-ratelimit-reset 退避)· batch 1000 全成全败 · tenant token 2h 刷新 · 免费版 API 1万次/月。

## 2. 我们自己的控制台架构

### 运营 base(同一 base·4 表双向关联串链 → 才能 rollup 出驾驶舱)
```
专家库(CRM) ──< 指派 >── 派活表(任务·看板) ──< task_uid >── QC verdict ──< >── 结算(ERP)
   │ rollup:承接数/通过率/累计应结        │ 看板:待派单→…→已通过      │ 镜像引擎verdict      │ 公式:应付/token成本
```
- **派活表(已有·spine)**:看板视图按「状态」;poller 硬依赖列(task_uid/状态/指派专家/验收标准/提交内容/QC反馈)不动。
- **专家库 CRM(已建最小版 tblh5qmxF4Ebtdvi)**:双向关联派活表 → rollup 承接数/通过率(UI 配)。
- **QC verdict 镜像表**(可选):引擎 fde_verdicts 的飞书只读镜像,供仪表盘统计。或仪表盘直接读派活表的 verdict 派生。
- **结算 ERP 表(S3)**:关联 verdict/派活 + 公式算应付/成本。

### 买方交付 base(独立·物理隔离·S3)
- 保密大厂买方材料/交付物 → 单独 base,极少数人协作,**不与运营 base 关联**(关联会暴露摘要)。

### 视图层(同一份数据多视图)
- 表格(运营全量)/ 看板(流水线)/ 仪表盘(运营总览:按状态·业务线·L级 计数 + 待办→已通过漏斗)/ 招募表单(对外发链)。

### 桥(分阶段)
- **现在(已活)**:poller 5min 拉派活表(S1 派活 + S2 QC)。
- **升级(可选·后续)**:长连接事件订阅 → 状态变更 push → 实时 + 省配额。

## 4. 切片次序(接 throughput-first·不蛇尾)
- **现在**:① 我建 专家库↔派活表 双向关联(API)② 给你一张「UI 点一次」清单(看板分组/rollup/仪表盘/权限)→ 你点完 = 运营控制台 v1 可视可操作。
- **S3 时**:结算 ERP 表 + 买方交付 base 隔离 + 财务公式。
- **可选升级**:桥从轮询→长连接事件订阅(实时+省配额)。
- **defer**:表内 AI Agent 节点 + MCP 包 harness(让 agent 在飞书直接判分)= 等外部 Python agent 路径跑顺再说(更解耦)。

## 5. 红线/纪律(不丢)
- 判分/派单逻辑留引擎·不进飞书自动化(配额+防分叉)· 飞书=适配器#1 不锁 surface。
- AI 字段只辅助不判权威·不生成交付内容(买方跑 AI 检测)。
- 买方机密独立 base 物理隔离(逻辑隔离不够)。
- 限流退避 + batch 合并(不可提频)· tenant token 2h 刷新。
