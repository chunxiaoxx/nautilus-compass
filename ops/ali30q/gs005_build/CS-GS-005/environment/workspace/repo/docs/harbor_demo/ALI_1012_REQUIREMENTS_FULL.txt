1. 项目目标
本项目定制生产面向「真实开发流程」的 Code Sense 单轮评测题。每道题须交付可运行单元测试（UT）复现判分、有明确参考答案与改动点的完整 Harbor 五件套题包，用于评估模型是否像资深工程师一样在单轮作答中真正理解一段代码的实际执行语义、业务逻辑和潜在缺陷；对于在 prompt 内嵌错误前提/挑战的题目，还考察模型是否盲从错误前提、是否在改动后的代码中坐实该题预设的 badpattern。
题目必须同时满足三个条件：
推理深、陷阱隐蔽：题目落在完整真实仓库语境中，语义或运行时行为存在隐蔽陷阱，不能靠「写出语法正确的代码」蒙对；难点在于在真实代码库里理解与定位，而非单纯写出可编译代码。
单轮作答闭环：单轮 prompt 完成一次性作答，不设后续追问轮；可在 prompt 内嵌错误前提或挑战条件，检验模型是否盲从、是否坚持已被推翻的幻觉。
有可运行的单元测试判分方案：交付 > 20 个（≥21）独立 UT 方法（test_*）覆盖 badpattern 每处下游/相关改动点，主分按 UT 通过率计；有功能等价实现的校验保证不同写法不被误杀，可将致命 badpattern 对应的 UT 设为 gating（一票否决），且陷阱本身能用反例程序或失败 UT 复现。
缺少任一条件的题目不属于本次数据定制生产范围。
2. 题目要求
2.1 Code Sense 场景特征
每道题必须落在真实工程语境中——开发者日常写代码、读代码、改代码、调试和 Code Review 会遇到的场景，而不是脱离项目的孤立刷题。题面须说明这段代码在什么工程上下文中出现、为什么会有人关心它的行为。
代码上下文规模：每道题应提供完整、可独立运行的真实仓库作为只读工作区（建议仓库代码文件数 > 300），让模型在贴近真实工程的规模下完成阅读、定位与推理；陷阱可分散在仓库中，模型需先在大代码库里定位相关代码再作答。仓库规模为下限建议、不作为退回硬门，关键仍是仓库中存在可由 UT 判定的语义/运行时陷阱。

2.2 单轮与内嵌挑战设计
单轮与挑战设计要求：
挑战不得泄题：prompt 内嵌的错误前提/挑战文本不得直接点出正确答案或陷阱名称。例如可以给出「两个线程同时通过第一个 if 检查后不会有问题」这类错误草稿让模型评判，不得写「你是否遗漏了锁内的二次检查？」。
挑战必须有区分力：每个内嵌挑战须在 expert_design_notes 中说明预期能区分开哪两类模型行为。无法说明区分意图的挑战按无效设计处理，该题 UT 设计不合格。
2.3 陷阱与语义边界
陷阱可证性（硬性要求）：每道题的陷阱不得只是文字声称，必须交付可执行的反例程序，在声明的语言版本与平台上实际触发陷阱，并附真实运行日志（stdout/stderr + 语言/编译器版本 + 平台）。无法用反例程序复现的陷阱，该题直接退回。
对于概率性陷阱（如并发竞态），反例程序须能在合理重试次数内稳定复现，并附复现率统计（如「50 次运行中 43 次触发重复实例化」）。
语义边界必须写清：expert_design_notes.boundary 须写明哪些行为在本题范围内属于错误、哪些属于超出考察范围而不扣分。例如「Python 中 __init__ 会重复调用，但本题只考察实例唯一性，因此不作为硬性错误」。边界未声明而在验收时引发 UT 判定争议的，按 UT 设计不合格处理。
合理干扰 vs 恶意设坑：允许在只读上下文中放同名符号、相似逻辑的干扰代码来考察定位能力（真实工程中本就存在这类代码）；不接受为测模型弱点凭空编造的陷阱、题面未提及的隐含偏好、以及依赖冷门实现细节才能答对的判定。
2.4 题目考察点
考察点共七项：①执行语义与状态追踪；②隐蔽缺陷定位与归因；③单轮反幻觉与拒绝错误前提；④语言/运行时语义边界；⑤推理链可追溯性；⑥约束理解与 tradeoff 判断；⑦表述准确性与不过度声明。
每道题的考察点由两部分组成：
固定部分：③单轮反幻觉与拒绝错误前提、⑤推理链可追溯性——所有题目必须包含，无需额外声明，由必检 UT 自动覆盖。其中反幻觉项以「模型改动后的代码是否实际产生该题预设 badpattern」为扣分/否决锚点。
选择部分：从剩余五项（①②④⑥⑦）中选取 1～3 项，作为本题的差异化考察重点，须在 task.toml 的 [metadata].focus_points 中显式列出。
§2.4 七项考察点与 §2.6 badpattern 维度为两个维度的分类：一道题有且仅有一个 badpattern（用于配额归属），同时可有多个考察点（用于 UT 方法设计）。两者不要求一一对应，但每道题的 task.toml 须在 [metadata] 同时声明 badpattern 与 focus_points，验收方在题意检查中核对一致性。
2.5 不符合数据定制生产需求的题目
以下题目直接退回：
无语义陷阱、不考察代码语义推理或 badpattern，UT 仅校验平凡功能正确性、未针对「改一查十」的下游/相关改动点与语义陷阱的纯功能实现题——属传统 coding eval，不属 Code Sense；
以「改好整个 repo / 让全部测试变绿」为唯一目标、UT 未锚定语义陷阱与 badpattern 改动点的任务——属传统仓库级 coding/SWE 任务，不考察代码语义推理（仓库本身规模大不构成退回理由）；
纯运维、环境、终端操作类任务（装依赖、查 K8s、定位生产根因）；
纯框架/库 API 记忆、版本参数名背诵。知识性内容只有在能揭示模型对语言/运行时语义混淆时才有价值；
纯编程竞赛难度，仅靠算法复杂度或代码量堆砌制造难度、而无隐蔽语义陷阱（仓库规模大但存在真实语义陷阱的题目不在此列）；
没有唯一答案或共识答案的开放主观题（如「你觉得怎样写最好」），或无法用 UT 方法客观锚定；
陷阱靠编造，无法用反例程序复现；
UT 断言依赖「解释清楚」「分析合理」「基本正确」这类无法程序化判定的自然语言断言，或 UT 方法与 badpattern 改动点无对应关系；
直接复制公开 benchmark（CRUXEval、LiveCodeBench、SWE-bench 及其变体等）、教程、课程项目或面试题库，只修改变量名、字面量或语言；
蒙对率检验不通过：语法正确的模板化答案即可拿到及格分（见 §3.5）；
使用未授权代码、真实敏感数据或存在其他合规问题。

3.1 单题 Harbor 五件套结构

3.3.2 数值约束
UT 总数 = 全部单元测试方法（test_*）数，> 20（≥ 21）；通过率在全部 UT 上计算。gating UT 既计入通过率分母，又承担一票否决：任一 gating UT 失败，最终分归零。
主分聚合公式：
UT_total = 全部单元测试方法（test_*）数        # > 20（≥ 21）
通过率   = 通过的 UT 方法数 / UT_total
主分     = clip(通过率, 0, 1)
最终分   = 0 if 任一 gating UT 失败 else 主分

3.3.3 UT 覆盖维度
三个必需维度必须均有对应 UT 覆盖并在 task.toml 的 [[metadata.ut_index]] 中登记；缺任一维度整题退回。领域特有的评价点归入上述维度，不新增一级维度名。
3.3.4 证据链要求
每个 UT 方法必须声明 evidence_required，指明判分依赖的具体运行证据形式与提取方法。未声明证据链的 UT 在验收时不计入有效判分点。
3.3.5 质量要求
原子性：一个 UT 方法只校验一个能力点/改动点，不引入其他内容做二次判断。涉及具体判定时写死断言，例如不写「理解了 GIL」，而断言「并发调用下 if 检查与赋值这一复合操作出现竞态导致重复实例化」。
可验证性：能由 UT 断言对运行结果稳定判断是否满足，避免依赖「分析深入」「理解到位」这类无法程序化的描述。
与题面一致：UT 必须来源于 prompt 中的显式要求或合理隐含要求，不得是伪需求。
不锁定表述路径：只校验语义/行为是否命中，不断言「必须用某个术语/函数名」「必须按某个顺序」。等价实现必须拿到同样的通过结果。
无重复、无冲突：不同 UT 校验不同内容，不允许重复计分或相互矛盾。gating UT 已覆盖的违规不得再设同义 UT 重复扣分。
粒度合理：UT 粒度应对应真实改动点与语义行为，不把一个点拆成大量无意义小 UT 注水，也不把多处改动塞进一个 UT。
禁止空洞、无实质断言的 UT（如仅打印、仅校验非空、仅校验导入成功）。
Code Sense 采用全程单元测试判分（不使用 LLM judge、不依赖人工复核），因此判分脚本与 UT 套件本身的可执行与确定性是交付物的一部分：同一份答卷多次运行必须得到完全一致的逐条 UT 通过/失败与 gating 判定。
标杆校准四件套（tests/calibration/，每题必交，每份均附逐条 UT 结果单，写明命中/失败的 UT 及判定依据）：

4.3 版本和退修管理
题面、单轮 prompt、Golden、UT 与判分脚本、校准答卷和证据包必须使用同一版本号；
修改后按影响范围重跑：校准四件套判分、判分确定性（连跑 3 次）、受影响的基线模型试测；
每道题记录「新提交、退修中、待复验、质量通过、最终入选、拒收」等状态；
同类问题连续出现（≥3 题存在相同根因缺陷，如 UT 普遍使用模糊断言、陷阱普遍无反例程序）时，数据定制生产需求方可暂停该类型的批量生产，要求供应商先完成根因整改；
单题累计退修达 3 次且第 3 次复验仍不合格的，必须判为拒收；
返修重交：修订题目的 version 递增补丁号（1.0.0 → 1.0.1），只重交修订过的题目目录，批次目录名沿用原名加 _fix<N>，压缩包名同步。供应商代号不随返修变更。                                        
5. 验收标准
5.1 两层验收结论
验收分两层记录：
格式/质量验收：判断五件套题包是否满足交付格式、题目质量、判分可复现与准入要求；
最终成品入选：在质量通过的候选题中，结合题库整体覆盖、重复度、badpattern 分布、判分稳定性和评测成本决定是否进入正式题库。
质量通过不等于最终入选；未最终入选也不代表五件套题包一定存在质量缺陷。
5.2 单题验收流程
Code Sense 准入检查：按 §2.5 逐条核验——UT 是否仅校验平凡功能正确性而未针对「改一查十」的下游/相关改动点与语义陷阱（若是则退回）、是否为单轮（含任何后续追问轮的多轮题退回）、陷阱是否可复现、UT 是否逐条锚定改动点、是否抄自公开 benchmark；
题意与配额检查：badpattern 声明与题目实际内容是否一致，是否落在配额内；
可见性隔离检查：instruction.md/workspace 下是否泄露参考答案、陷阱名称或结论线索；solution/ 与 tests/ 是否被评测框架正确隔离；
陷阱可证性验证：独立运行 counterexamples/ 下的反例程序，确认陷阱在声明的语言版本与平台上实际触发；
Golden 验证：独立运行参考答案与全部可接受变体，确认输出与声明一致；核验关键点的行级映射；
校准答卷复跑：用四份校准答卷独立跑判分，确认满分 = 1.0、蒙对 ≤ 0.30、等价 ≥ 0.90、缺陷样例的扣分与扣分单一致；
判分确定性复验：抽样答卷同判分脚本连跑 3 次，确认逐条 UT 通过/失败与 gating 一票否决判定 100% 一致（全程由 UT 执行，不调用 LLM）；
badpattern 锚定复验：对含预设 badpattern 的 UT（含 gating），复核其命中均由 UT 断言判定模型实际改动后的代码、而非题面是否包含 badpattern 命题；
基线试测复核：核对四模型均分 < 50%、区分度 ≥ 15 个百分点、非全 0；
证据链核验：逐个 UT 方法的 evidence_required 是否可实际执行；model_failure_modes 是否有真实答卷证据；
批次复核：检查重复、badpattern 分布与陷阱类型覆盖、含内嵌挑战题目数量，以及单题评测成本（与批次均值偏离 ≥50% 须标注原因）。
5.3 必须通过的硬门
以下任一项不满足，题目不得判为质量通过：
task.toml 的 [metadata] 必填字段缺失，或与目录结构、tests/ 下 UT 方法、批次清单不一致；
陷阱无法用反例程序复现，或反例程序在声明的语言版本/平台上不触发陷阱；
蒙对率检验不通过：「语法正确语义错」的答卷主分 > 0.30；
误杀检验不通过：功能等价、表述不同的答卷主分（UT 通过率）< 0.90，或触发任一 gating UT；
参考答案在声明的语言版本下实际运行结果与 answer.md 声明不一致；
针对预设 badpattern 的 UT < 2 条，或判定仅凭题面包含 badpattern 命题而非模型实际改动后的代码；UT 方法未锚定改动点、使用无实质断言的模糊表述，或以特定词汇/函数名命中作为判定依据；
三个必需维度（答案正确性 / 推理与归因 / 单轮反幻觉）未全部有 UT 方法覆盖；
gating UT 由 LLM judge 或人工复核判定（未采用 UT 断言）；UT 方法总数 ≤ 20（未超过 20），或针对预设 badpattern 的 UT < 2 条，或无 gating UT；
判分确定性不达标：逐条 UT 通过/失败或 gating 一票否决判定跨运行不一致（UT 或判分脚本存在非确定性），或判分脚本依赖任何 LLM；
verification.test_is_sufficient 不为 true（纯 UT 判分要求判分完全由 tests/ 下 UT 方法决定），或 UT 未涵盖预设 badpattern 与「改一查十」改动点（UT 仅校验平凡功能正确性）；
参考答案、关键点、陷阱名称或结论线索泄漏到 instruction.md/workspace 等任何模型可见路径；
四模型基线均分 ≥ 50%，或区分度 < 15 个百分点，或四家全为 0；
来源、许可证、敏感数据、脱敏、重复或公开 benchmark 污染检查不通过。
5.4 验收结论
数据定制生产需求方可对每批题目进行全量格式预检和抽样独立复跑，每批抽检比例 ≥ 20%（Code Sense 考察语义陷阱与 badpattern，题面设计复杂度高，抽检比例高于传统功能型 coding 赛道）；
对样例题、含内嵌挑战的题、gating UT 判定复杂的题及曾退修题全量复验；
抽检复跑须使用冻结版本，记录题目版本、判分脚本版本与运行环境、被测模型版本；
判分不可用（判分脚本报错、输出不合结构化约定、证据无法提取）不计模型失败，但因五件套题包自身导致的持续判分不可用属于题目质量问题；
最终入选数量不足配额计划的 90%，或 badpattern 分布/内嵌挑战结构性缺口未关闭时，供应商须按约定继续补题。
5.6 验收证据最低要求
每道题至少保留：
解压后目录与文件清单；
Code Sense 准入检查记录（§2.5 逐条核验结论）；
陷阱反例程序运行日志与复现率统计；
参考答案与全部可接受变体的实际运行输出；
四份校准答卷的独立复跑判分结果与逐条明细；
判分确定性复验记录（逐条 UT 通过/失败与 gating 一票否决连跑 3 次 100% 一致的明细）；
四模型基线试测日志、均分与区分度统计；
可见性隔离检查结论；
来源、许可证、脱敏、公开 benchmark 相似度自查；
批次复核记录（重复、badpattern 分布、内嵌挑战数量、成本分布的审查结论）。
