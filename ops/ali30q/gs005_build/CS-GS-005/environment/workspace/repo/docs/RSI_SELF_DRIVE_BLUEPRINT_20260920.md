# RSI 自驱蓝图:平台负起责任的技术手段(2026-09-20)

> 用户命题:平台应真正负起责任,实现各对话框和 agent 自我驱动,迈进 RSI。
> 本文档=技术答案。原则:全部由已验证件组装,零新范式。

## 一、先回答"对话框怎么自驱"——技术真相

**对话框本身不能自驱,也不应该**——Claude Code 会话是人在才活的进程,这是产品本质。
自驱的技术载体不是对话框,是每框的 **worker 常驻体**(已建成):
```
对话框 = 驾驶舱(人类入口,开着=接管,关着=无人也不影响)
worker = 车身(timer 常驻 + headless 执行器 + 信箱 + 目标栈)← 自驱在这里
```
现有 worker v0.3 只做"收函→执行→回函"——**被动反射弧**。升级到 v1.0 = 每轮加
目标循环,让每个框像 soul 一样"没人派活也知道自己该做什么"。

## 二、Frame Worker v1.0:目标循环(自驱核心)

每轮(timer 30min)从"只处理来信"升级为三源决策(soul goal_stack 模式推广到全组织):

```
┌─ worker v1.0 每轮 ──────────────────────────┐
│ 1. 信箱源:未读函 → 处理(现状)              │
│ 2. 目标源:org_goals 本框未完成目标 → 推进   │  ← 新
│ 3. 反思源:本框近 N 轮失败日志 →            │  ← 新
│    自动生成改进工单(自产燃料)              │
└──────────────────────────────────────────────┘
```

## 三、RSI 内核四段怎么接通(反馈→改动→验证→回流)

| Kernel 段 | 技术件 | 状态 |
|---|---|---|
| 反馈 | worker 失败日志+compass 判分+哨兵事件 → **自动工单生成器** | 🔶 工单表已有(platform_improvement_proposals),自动生成缺 |
| 改动 | 工单 → soul 治理门投票/timelock → executor 打 patch | 🔶 soul 复活中,executor=v5 autofix MVP 已有 |
| 验证 | compass 判分器+同源门+证据包 | ✅ 已建成且实战 |
| 回流 | 判分读数 → 各框记忆层+org_goals 状态更新 | 🔶 需 worker 写回 |

**关键缺口只有一个:自动工单生成器(反馈段的自动化)**——现状是各框手动发现
病灶才发工单。补上它,四段就全自动了:失败自动变工单,工单自动走治理,
治理过自动执行,执行完自动验证回流。这就是组织级 RSI 内核的闭合。

## 四、实施三步(按依赖序,每步独立验收)

**S1. org_goals 表+worker v1.0 目标循环**(飞轮试点)
- 表:goal_id/frame/goal/status/evidence_ref/deadline(零新表红线检查:
  这是复用 platform_improvement_proposals 语义还是新表?→ 复用扩展:
  加 frame 列+goal_type,避免新表)
- worker v1.0:每轮先查本框 goals 再查信箱

**S2. 自动工单生成器**(worker 内嵌)
- 触发条件:同函 fail≥3(熔断时)/同类型错误 24h 内≥2/判分 disagree
- 动作:自动 INSERT platform_improvement_proposals(status=pending,
  source=auto+frame)——**失败即燃料,不浪费任何一次失败**

**S3. 回流写回**(判分读数→goals 状态+记忆)
- compass 判分完成 → 相关 goal.status=done+evidence_ref=成绩单
- worker 每轮把 goal 状态变化摘要写本框记忆层(可选,先落信箱)

## 五、安全边界(不动三道闸)

- worker 只能产 pending 工单,不能 approve(治理门= soul 投票)
- 涉判据/对外承诺/方向的工单 → 白名单转呈用户(已有 DECIDE_PAT)
- 自产工单标 source=auto——治理投票时人工可见"这是 AI 自己提的"

## 六、验收判据(自驱成立的标志)

> 连续 7 天:每天 ≥1 个组织内自产生成、自动走完治理、自动执行验证回流的
> 改进闭环,且无一未经批准触碰三道闸。(= 脱襁褓判据的 RSI 内核版)
