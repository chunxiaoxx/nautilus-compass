# Phase 3 飞书多维表格表单蓝图

> **历史设计探索，不作为当前写入契约。** 当前两阶段流程以
> [FDE_PHASE3_BITABLE_AUTHORITY.md](FDE_PHASE3_BITABLE_AUTHORITY.md)、
> canonical schema module 和 [飞书绑定 Runbook](FDE_PHASE3_FEISHU_BINDING_RUNBOOK.md)
> 为准。以下内容只保留为未验证的历史快照，不代表当前线上状态。

## 目标

让外部专家只完成一次简洁的 Evidence Pack 提交，让内部人员在同一 Base 内完成
P0、买方反馈、返修和导出回执。任务状态和审核结论只以 Bitable 的 read-back 为准。

外部人员不需要了解 V5、Compass、`revision_of`、导出状态或内部评分规则；这些由
受控角色和系统处理。

## Base 与身份原则

- 复用经确认的第三期 Base，不创建第二本台账。
- Bitable 原生 `record_id` 是每类记录的唯一身份锚，不建立可编辑的替代编号字段。
- `task_code` 仅供运营和外部人员沟通，不是导出身份。V5 仅在受控路径中由任务
  `record_id` 派生不透明 `task_id`。
- 外部证据、分享引用和平台日志标识只保存在受限字段或受限附件中；不进入 Git、
  Compass、对话框、通用导出或公开视图。
- `revision_of` 是“交互尝试”对自身的单向关联，只指向直接前序尝试。

## 已落地的空 schema

当前内部 Base 已建立以下六张业务表，并逐表 read-back 了字段名、类型与关联。
它们均为零业务记录状态：

| 物理表 | 角色 | 约束 |
| --- | --- | --- |
| `外部题目提交` | 原生表单的题目/返修提交入口 | 只保存一次提交；受控适配器才可建立任务和尝试关系。 |
| `任务` | 任务契约和业务状态 | `task_code` 仅为运营标识，`record_id` 才是身份锚。 |
| `交互尝试` | 多轮交互与返修血缘 | 已有任务关联、提交入口关联和自关联 `revision_of`。 |
| `审核` | P0、反馈类别、甲方状态和 `verdict` | 人工写入；自动化不得给出通过结论。 |
| `导出与回执` | 脱敏事件、manifest 与 Compass 回执 | 只在 eligible 后由受控路径写入。 |
| `专家申请` | 招募筛选、培训和豆包开通门槛 | 不收集银行卡、身份证、账号密码或任何凭据。 |

飞书自动生成的一张空 `数据表` 未被纳入业务流程，也不是权威记录来源；在
Base 所有者确认后可在界面中删除或另作无状态占位使用。文档不记录 Base token、
table ID、record ID 或任何个人资料。

## 最小表结构

### 0. 外部题目提交

该表是外部专家唯一的题目/返修表单源，不是第二本任务账本。它保存题目契约、
提交模式、工具、开始与提交时间、轮次数、证据附件、最终产物、分享引用、平台
日志标识和本人确认。`关联任务`、`关联尝试` 与 `入口状态` 是内部受控字段，
不出现在外部表单。

### 1. 任务

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `task_code` | 文本 | 运营可读的任务编号；不可用于导出身份。 |
| `title` | 文本 | 一句任务名称。 |
| `business_status` | 单选 | `draft`、`assigned`、`evidence_submitted`、`p0_review`、`buyer_review`、`accepted`、`repair_required`、`rejected`。 |
| `category` | 单选 | 沿用买方一级分类。 |
| `task_type` | 单选 | 任务类型；映射以买方已批准枚举为准。 |
| `task_prompt` | 长文本 | 必填。完整题目、背景、约束和允许工具；不能仅用截图或聊天记录替代。 |
| `attachment_format_tags` | 多选 | 必填。说明所需或提交的附件格式与标签。 |
| `source_materials` | 受限附件或受限引用 | 必填。题目所依据的材料；原件不进入 Git、Compass 或通用导出。 |
| `expected_output` | 长文本 | 必填。说明期望产物、交付格式和验收要点。 |
| `key_steps` | 长文本 | 必填。完成题目的关键操作步骤或必须覆盖的推理/工具链。 |
| `assignee` | 成员或受控文本 | 外部专家的最小必要联系锚；不导出。 |
| `current_attempt` | 关联到交互尝试 | 当前待审或已通过的尝试。 |
| `created_at` | 创建时间 | 审计字段。 |

### 2. 交互尝试

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `task` | 关联到任务 | 必填；每次提交只关联一个任务。 |
| `attempt_no` | 数字或公式 | 同一任务内递增；用于人工识别，不替代 `record_id`。 |
| `attempt_status` | 单选 | `evidence_submitted`、`p0_failed`、`buyer_review`、`repair_required`、`accepted`、`rejected`。 |
| `revision_of` | 自关联到交互尝试 | 返修必填，且只指向直接前序尝试。 |
| `tool_name` | 单选 | 当前期默认“豆包办公任务”；保留受控枚举以兼容后续允许的工具。 |
| `started_at` / `submitted_at` | 日期时间 | 用于时限核验。 |
| `turn_count` | 数字 | 申报值；P0 复核后才可作为有效证据。 |
| `evidence_pack` | 受限附件或受限引用 | 截图及最终产物；仅授权审核角色可见。 |
| `share_reference` / `platform_log_id` | 受限文本 | 外部平台引用；不得进入脱敏导出。 |
| `operator_attestation` | 勾选 | 声明为独立、完整交互；不是 P0 通过证据。 |
| `redaction_status` | 单选 | `pending`、`verified`、`failed`。 |
| `trajectory_hash` | 文本 | 受控服务生成的证据摘要；不存原始逐轮内容。 |

### 3. 审核

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `attempt` | 关联到交互尝试 | 必填；一次审核只对应一个尝试。 |
| `p0_status` | 单选 | `pending`、`pass`、`fail`。 |
| `p0_failure_classes` | 多选 | 仅记录失败类别，不自动生成最终判定。 |
| `trajectory_coherence` | 单选 | `pass`、`fail`。 |
| `feedback_class` | 单选 | `none`、`accepted_advisory`、`revision_required`、`rejection_reason`。 |
| `buyer_status` | 单选 | `pending`、`accepted`、`revision_required`、`rejected`。 |
| `verdict` | 单选 | `pending`、`Gold`、`Repair`、`Reject`；只允许审核人写入。 |
| `reviewer` / `reviewed_at` | 成员、日期时间 | 审计字段。 |
| `review_proof_hash` | 文本 | 受控的审核摘要，不保存原始买方意见。 |

### 4. 导出与回执

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `attempt` / `review` | 关联 | 必填，关联交互尝试与审核。 |
| `export_status` | 单选 | `not_eligible`、`canonical_pending`、`canonical_verified`、`canonical_blocked`、`compass_imported`。 |
| `eligibility_reason` | 长文本 | 只记录受控门槛原因或阻断原因。 |
| `opaque_task_id` / `event_id` | 文本 | 由 V5 受控生成；不写入 Bitable 原生记录身份。 |
| `payload_hash` / `manifest_hash` | 文本 | 官方 v3 脱敏导出和 manifest 的摘要。 |
| `compass_receipt_hash` | 文本 | Compass 回执摘要。 |
| `exported_at` / `received_at` | 日期时间 | 审计字段。 |

### 5. 专家申请

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `申请编号` | 文本 | 运营识别，不替代 Bitable `record_id`。 |
| 联系、学历、工作年限、行业、领域、参与方式和来源 | 最小必要的文本/单选字段 | 仅用于招募与联系，表单展示隐私告知和联系授权。 |
| `Agent使用经历` | 多选 | 兼容豆包、WorkBuddy、TRAE、ChatGPT、Claude 和其它工具。 |
| `申请状态` / `培训状态` | 单选 | 人工筛选和培训过程。 |
| `首个任务完成` / `豆包开通状态` | 勾选、单选 | 只有人工确认报名通过、培训完成并完成首个任务后才可进入 `eligible_to_open`。 |
| `运营负责人` / `内部备注` | 受限内部字段 | 不出现在外部表单。 |

## 两个外部入口，三个内部视图

### 外部表单：新题提交或返修交互成果

该表单将基于 `外部题目提交` 发布，有两个受控模式，且字段说明直接显示在
对应输入框旁：

- **新题提交**：外部专家必须填写题目、任务类型、附件格式标签、来源材料、期望产物和
  做题关键步骤，并提交使用工具、开始与提交时间、轮次数、Evidence Pack、分享引用、
  平台日志标识和提交声明。受控适配器在字段映射获批后，以同一幂等键创建一个 `draft`
  任务和一个关联的首个交互尝试；尝试状态为 `evidence_submitted`。
- **返修提交**：外部专家只选择已分配的任务编号并补交新的交互成果。受控适配器在内部
  解析直接前序后，创建一个新的交互尝试；外部表单不展示或写入 `revision_of`。

两种模式都不得写入 P0、买方结果、`verdict`、内部返修血缘或导出状态。当前期表单校验
至少包括模式匹配的必填业务字段、工具枚举、`turn_count >= 6`、完成时间和提交声明。它们
仅阻止明显缺项，不能替代人工 P0。

表单只显示：提交模式、返修任务编号（仅返修时）、题目契约、工具、开始与提交
时间、轮次数、对话证据、最终产物、分享引用、平台日志标识和本人确认。必须隐藏
提交编号、入口状态、两个内部关联字段，以及所有审核与导出字段。

### 外部表单：专家申请与豆包开通

该表单将基于 `专家申请` 发布，用于收集姓名或称呼、飞书联系方式、手机号或
邮箱、学历、工作年限、职业或行业、专业领域、全职/兼职意向、招募来源、Agent
使用经历、可开始时间与隐私联系授权。它不收集结算资料、银行卡、身份证、账号
密码或豆包凭据。

必须隐藏申请状态、培训状态、豆包开通状态、首个任务完成、运营负责人和内部
备注。豆包权益不因提交表单自动开通；人工确认报名通过、完成培训和首个任务后，
运营人员才可将状态改为 `eligible_to_open`。

### 内部视图

| 视图 | 使用者 | 最小用途 |
| --- | --- | --- |
| `待 P0` | 内部审核 | 核验互动完整性、连贯性、脱敏状态和 Evidence Pack。 |
| `待买方与返修` | 审核与运营 | 登记买方结果、反馈类别；建立返修尝试及 `revision_of`。 |
| `可导出与回执` | 受控 V5/Compass 操作人 | 只查看 eligible 项、manifest 和回执；不改业务 verdict。 |

另设仅管理员可见的 `审计只读` 视图，用于回查所有关联、时间和状态变化。

## 权限与自动化边界

- 外部专家：仅使用表单；不直接访问 Base，不查看其他人的记录。
- 审核人：可读受限证据并写审核记录；不能手工伪造 V5 hash 或 Compass 回执。
- 运营：管理任务分配和返修路由；不能覆盖审核人的最终 `verdict`。
- `ecc-shared` 受控身份：唯一可进行 Bitable schema 校验、幂等写入、脱敏和 read-back
  的自动化身份；上线前需单独授权。
- V5：只读 eligible 记录并写导出记录的受控字段；不改买方结果和血缘。
- Compass：不直接访问 Bitable；只消费 V5 的官方脱敏 JSONL 与 manifest，并返回受控
  回执供受权操作人写回。

任何公式、自动化或 AI 建议都不得自动把 P0、`buyer_status` 或 `verdict` 改为通过。

飞书原生表单的创建当前不由已验证的服务端 API 或既有 CLI 覆盖。Base 所有者必须
在飞书界面以 `外部题目提交` 和 `专家申请` 两张源表分别新建并发布表单；发布后
由 `ecc-shared` 读取表单源表及 schema，不接受聊天截图作为配置完成证据。

## 首条记录的验收演练

在获准实施后，以一条经授权的任务执行以下演练：

1. 由外部新题表单提交完整任务规格与交互成果；受控适配器创建一个任务和一条首个关联
   交互尝试。
2. 审核人完成 P0、反馈分类和最终判定；返修时单独创建新尝试并填写 `revision_of`。
3. 受控 read-back 核验 `turn_count`、P0、`feedback_class`、`verdict`、脱敏和血缘。
4. V5 仅为 eligible 记录生成 v3 JSONL 与 manifest，并将摘要写入导出记录。
5. Compass 先 dry-run，再执行幂等导入与 read-back；受权操作人记录回执。
6. 管理员在 `审计只读` 视图复查四类记录的关联和状态，确认没有缺项或越权写入。

完成前不得宣称该任务已闭环；任一步失败都保留阻断原因并停止下游动作。

## 待完成的实施项

1. Base 所有者按上述字段可见性发布两张原生表单，并把表单链接给内部运营确认。
2. 明确买方新 Base 的字段名与枚举映射；只读取 schema，不读取原始验收行。
3. 指定首条授权任务、外部专家范围和买方反馈录入人；P0 继续由组织内指定审核人负责。
4. 配置 `ecc-shared` 的最小字段权限、附件保留期限和表单提交到任务/尝试的受控写回门。
5. 完成一次一条记录的人工 P0 演练后，才可评估 V5 v3 脱敏导出与 Compass 回执。

原生表单发布、受控写回、买方同步、V5 官方导出和 Compass 正式导入仍然冻结。
