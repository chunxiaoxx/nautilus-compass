质检方案（CodeSense 定制）
为了降低单个 task 的质检时间、提升整体 dataset 的质检效率，质检工作围绕质检清单 checklist 展开。清单由质检项 checkitem 组成，每项是执行和复用的最小单位，结论分别记录；检查项可共享证据，也可存在明确的证据或执行前置依赖。每项包含如下核心内容
检查项描述：对于质检项内容的描述
检查项分类：对于质检项内容的一个大致分类
检查对象：质检进行需要针对哪些文件，目录等信息
检查方式：用什么方式进行质检，具体枚举如下
检查标准：pass和fail的标准
检查项描述
一段简短明确的文字描述该检查项在检查什么内容
检查项分类
检查项的一个分类方法。参考Mercor的分类法，结合项目中的分类，将检查项分为：
格式合规/Format Compliance：对目录layout，文件内容格式的检查
题目质量/Question Design：针对题目质量的检查
任务有效性/Specificity：题目是否明确无歧义，指令是否自包含
任务可解性/Solvability：验证 Oracle 方案确实能完成任务，且方式真实可行
任务完整性/Integrity：没有答案泄露；NOP/空实现不能通过任务，不要求原本正确的回归用例全部失败
环境校验/Environment：确保 Docker 环境确定性、自包含、可复现
验证器/Verifier & Verdict：验证 UT 测试套件的正确性、覆盖和通过判定，确保结果可复现、可追溯；模型成绩仅用于分析任务难度
检查对象
检查对象分为 task、jobs，以及 task-jobs 交叉证据。例如，Harbor 格式校验针对 task 的目录布局。为便于执行、复用和转换为检查脚本，每个检查项应明确需要读取的文件、配置或运行结果。
检查方式
原则：尽量将质检工作左移，将问题暴露在更早阶段；能确定性验证的事项使用程序检查，需要理解需求或判断证据含义的事项由人工 Review。两者只产生数据质检结论，不改变任务的 UT 结果。
程序性检查：通过静态解析、测试收集、运行探针、UT 执行、结果核对和重复运行进行确定性检查。程序性检查不等同于只做静态检查。
人工 Review：审查题面语义、需求与测试的对应关系、测试公平性和失败归因。结论须引用文件、断言或运行证据；必要时补充可复现实验或交叉复核。
检查标准
每项应明确检查内容和 Pass/Fail 标准，并遵循前述 Flag/N/A 约定。配置未给出时不得臆造测试数量上限、通过线、复跑次数或额外验收条件。项目规定的通过规则应仅使用 UT 通过/未通过状态及已声明的 gating 门槛。
