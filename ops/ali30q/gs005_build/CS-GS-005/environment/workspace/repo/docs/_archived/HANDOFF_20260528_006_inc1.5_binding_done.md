## Section 3 · Bugs found during binding-done verify

### 3.1 Bug 1 · executor `resolved_by IS NULL` excludes auto_stale rows · FIXED in PR #66

**Symptom:** Path B Phase 1a achieved `status='accepted'` + `resolved_by='auto_stale'` but soul executor's first cycle reported `0 proposals processed` even though the row was valid.

**Root cause:** Inc 1 executor query (`soul_executor.py:88`) filtered `AND resolved_by IS NULL` to prevent double-pickup. Inc 1.5 stale-approve sets `resolved_by='auto_stale'` at the same UPDATE that flips status to 'accepted' (per Inc 2 NAU hook discriminator design). Therefore stale-approved rows were invisible to the executor — a pure Inc 1 ↔ Inc 1.5 boundary gap; both 31/31 + 15/15 unit tests passed individually because they did not cross the boundary.

**Fix:** Expand pickup predicate to `(resolved_by IS NULL OR resolved_by = 'auto_stale')`. Preserves "soul has not touched it" semantics (NULL) AND adds the "stale-approve fail-safe touched it but ship is still owed" state (auto_stale). After ship, `_writeback` sets `resolved_by='soul'` so the row exits this window; idempotent · no double-ship risk · no schema change · no behavior change for non-code rows.

**PR:** [#66](https://github.com/chunxiaoxx/nautilus-core/pull/66) (open · draft=false · awaiting merge).

**Cloud workspace:** patched in-place at `/home/ubuntu/nautilus-soul-workspace/phase3/backend/services/soul_executor.py` with `.bak_inc1_5_fix_*.py` backup. The Path B Phase 1c proof in Section 1 used the in-place patch (i.e., the chain only works after this fix).

**Symptom:** Path A target's 3rd vote pushed past consensus threshold; vote endpoint returned `status='approved'` instead of `'accepted'`. Executor query is `WHERE status = 'accepted'`, so the vote-driven path could not reach the executor. Manual `UPDATE ... SET status = 'accepted'` was used to bypass this and verify the rest of the chain.

**Root cause:** `proposal_consensus.get_proposal_status` on cloud (`soul-audit-increment1` branch) returns the V3 sandbox legacy `'approved'` literal at consensus. Origin/master already returns `'accepted'` (the Inc 1 keystone artery alignment). The cherry-pick of the Inc 1.5 squash commit only brought in Inc 1.5-specific changes; the earlier "approved → accepted" change pre-existed in master before Inc 1.5 was branched and was therefore NOT in the squash diff.

**Why no master commit needed here:** This is a cloud divergence issue, not a code gap. Origin/master is already correct. The clean remedy is for cloud to eventually re-base / re-sync onto master (~ 756 commits behind today per `git rev-list --left-right --count origin/master...HEAD`); this is documented as Open Item 4 in Section 5.

**Workaround used in Section 1:** manual `UPDATE ... SET status='accepted'` for Phase A target only. Inc 1.5 followup verifications will not be relied upon if they require cloud's vote endpoint to write 'accepted'; either insert via the stale-approve path (which correctly writes 'accepted') or accept the manual UPDATE step.
