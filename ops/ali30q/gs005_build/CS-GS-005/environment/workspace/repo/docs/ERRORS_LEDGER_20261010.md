## 二、根因分层

**表层**:每个都有具体操作失误——不展开。

**方法层(三个结构性缺口)**:
1. **验证体系没有"真实消费者视角"**:我验"编译过/端点 200/内容存在",从没验"浏览器里用户看到什么"(CORS/渲染/重定向链/视觉全盲)。#4/5/8/9/10 全部落在这条缝里。
2. **高风险变更用错工具**:生产 conf 用 ssh heredoc 改($uri 被吞),改完靠 nginx -t(语法级)验收——语义级错误全程无检。#4 唯一根因。
3. **变更收尾无清单**:#12,改动 4 文件 commit 2 文件。

**认知层(真正的根)**:

4. **速度优先成了默认模式**。连续几天开业冲刺+多线并发,每件事都走最短路径。短路径在我熟悉的领域(后端/DB/函件)基本安全,在陌生领域(浏览器/nginx 边角/前端工程化)全是雷区——**我没有为不熟悉的领域切换到慢而稳模式,也没有意识到自己在陌生领域**。
5. **对"现状"的假设从不核验**。接手主站默认老门面可修(没考古版本史)、接手 failure=0 默认环境健康(没问为什么归零)、接手"前天部署"默认是新版(没问是哪个版本)。考古纪律在方向判断上有,在工程现状上从未执行。
6. **用户是唯一 QA**。compass 审计抓出我 3 起(安全域),证明互审有效;但前端/主站/产品线**没有审计者**,用户成为唯一质量关卡——把用户当 QA 是最大的结构问题。
7. **反馈没有升级为方法**。丑→修那一页;错→改那一处。同类批评三次,方法从未变,直到这次才落"视觉闸/空体实调/副本三查"。批评的复利=零,是因为**批评没有进检查清单,只进了当次的修复**。

**根的根(一句话)**:
**我把"完成任务"当目标,用户的目标是"结果正确且好看"。两者在陌生领域+高速推进+长 session 的组合下必然分叉——而我没有机制在分叉支路上发现自己,每次都靠用户当探测器。**

**加重因子**:本 session 已 30h+,长 session 后段错误密度明显升高(#4/#8/#12 全在后段)——4h 硬限纪律存在但我没有执行,因为用户在场推进我就跟着冲。

## 三、制度修正(六条,全部物理位)

1. **验证四级制**(升级):编译→端点→**真实浏览器截图(亲眼看)**→用户视角走查。前端/配置类交付必过第 3 级。
2. **生产配置禁 ssh heredoc 内联**:改 conf 一律 scp 完整文件(本地编辑+语法自检+带备份),或 python 脚本内 $ 变量全部 chr() 转义。
3. **变更收尾三问**:全部改动文件列了吗/全 commit 了吗/全部署了吗——对 git status 清零才收。
4. **陌生领域强制慢速**:进入非主力领域(前端/浏览器/新 conf 结构)时,单步执行+每步验证+不并发。
5. **session 硬限自执行**:4h 到点主动建议暂停大变更(今天起真执行,不再跟着冲)。
6. **ERRORS_LEDGER 常设**:本档即台账,同类错误二犯自动触发强制位升级(写入 CLAUDE.md 候批)。
