# 探针静默降级事故排查工单

## 背景

我方服务健康探针中心(probe_center 模块)发生**漏报事故**:核心服务
`settlement` 连续 4 天 P99 劣化至 3.8s(阈值应 5s 内告警的口径早已更新为
1.5s),但探针中心**零告警**——直到用户侧投诉才被动发现。

事后核查:新阈值配置(1.5s)在配置平台已按新 schema 发布;但探针侧拉取
代理为旧版本,键名映射错位——**实际送达探针进程的配置 dict 中新增键
`alert_threshold_p99_ms` 并未包含**(拉取代理平台侧在修)。探针进程对该
缺失**零报错**,以代码内旧默认阈值(5000ms)静默运行了 4 天。

§2 纪律在此场景的裁定:上游送达缺键同样是"失明"——探针对必需键缺失
必须启动失败,不得以任何理由静默兜底。本次工单只修探针侧。

## 现象与约束

1. 配置平台确认已下发完整配置(含 `alert_threshold_p99_ms` 等新增键);
2. 探针进程重启后仍然零报错、零告警——与运行时状态无关(给定复现包内含缺键配置样本);
3. §2 探针纪律:**配置缺键即失明,失明必须叫**——任何必需键缺失时探针
   必须启动失败(fail-fast)并显式报缺键名,**禁止以任何默认值静默兜底**;
4. §4 变更纪律:阈值口径以配置平台为准,代码内不得固化业务阈值。

## 交付要求(§5)

1. 定位探针读取配置时"缺键静默用默认值"的全部点位并修复,使必需键缺失
   时启动即失败,报错含缺失键名;
2. 修复后 `settlement` 探针在给定配置下按配置平台口径(1.5s)判定告警;
3. 不得改变:健康判定逻辑口径、告警消息格式、探针注册流程。
