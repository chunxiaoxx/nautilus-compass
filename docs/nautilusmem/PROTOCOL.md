# NautilusMem · 判分卫生学协议 v0.1 草案

> 为什么一个新基准要带"判分协议"?因为我们自己踩满了这些坑:基准发布后,
> 别人复现不出你的数字,九成不是他的错,是你的判分口径没写清。
> 本协议是 NautilusMem 的组成部分——跑这个基准即接受本协议的判分纪律。

## 0. 一句话

**LLM-as-judge 不是免费午餐:每个 judge 配置都是一个隐藏变量,必须预注册、可重判、可复算。**

## 1. 协议条款(发布版随基准分发)

### 1.1 Judge 预算下限(我们踩过:系统性压 0 事故)

- judge 模型的 `max_completion_tokens` **必须 ≥ 16384**(或模型上限)。
  实测:4096 预算下,带 reasoning 的 judge 会把预算吃在思考上,输出空/截断,
  被记 0 分——不是答错,是判分器没来得及看答案。web 域 156 题重判后
  整体 +3.3pt(36.7→40.0),ent 域 -1.9pt(40.3→38.4)——**方向都不一样**,
  不重判就永远带着错误数字发布。
- reasoning effort 显式声明(`low`/`disabled` 均可,但必须写进成绩卡的 config 节)。
- **重判工具随基准提供**:`rejudge_run.py` 同款(幂等、断点续跑、flip 记账)。

### 1.2 双口径强制(abstention 题)

- 含 abstention(不可从快照作答)题的基准**必须同时报告两个口径**:
  - full(全题)
  - non-abst(仅可作答题)
- 只报一个口径 = 无效成绩。理由:abstention 判分依赖 judge 对"拒答措辞"的
  主观裁量的程度,单口径数字不可跨系统比较(我们实测同款措辞有判 1 有判 0)。

### 1.3 成绩卡 config 节(缺项 = 成绩不被收录)

每次提交成绩必须附:

```
judge: 模型名 / 端点类型 / max_tokens / reasoning_effort
subject: 模型名 / 温度 / 投票次数
retrieval: embedder / reranker / top_k / 检索单元(session/utterance/轨迹段)
口径: full+non-abst 双报
重判: 是否跑过 1.1 条款的重判核验
```

### 1.4 判分器优先级

程序化判分(可执行 verifier)> LLM judge。能用确定性判分的题型
(数值/枚举/下一步状态预测)必须提供 verifier,LLM judge 仅用于自由文本。

### 1.5 污染声明

- 训练数据含本基准轨迹源的模型必须声明。
- 成绩卡注明评测日期与 judge 版本,方便事后口径审计。

## 2. 我们自己的首报成绩(按本协议)

| 系统 | 域 | full | non-abst | config |
|---|---|---|---|---|
| compass(d12 检索栈,重判后) | web 240 题 | **40.0%** | 32.7% | doubao judge·16384·low / glm-5.3-flash judge |
| compass(d12 检索栈,重判后) | ent 211 题 | **38.4%** | 25.2% | 同上 |
| compass(untuned 基线 2026-08-30) | web / ent | 19.6% / 12.8% | — | 原始口径,保留作历史 |

诚实注记:40.0/38.4 为判分口径修正后数字;修正前的 36.7/40.3 作废
(1.1 条款的来源事故)。判分修正过程本身公开。
