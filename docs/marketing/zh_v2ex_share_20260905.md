## 标题

[分享] 写了个开源的 agent 长期记忆层:写入路径零 LLM 调用,长跑 130 天的自用项目

## 正文

背景:给 AI agent 做长期记忆,业界的常见做法是写入时用 LLM 做压缩/提炼。我的判断是这条路有结构性问题——写入时你不知道未来会被问什么,压缩就是盲目下注;而且存储越来越便宜、推理越来越贵,拿存储换推理调用方向是反的。

所以我反着做了一套:nautilus-compass

- 写入:观察原文逐字入库(SQLite),嵌入用 BGE-m3 本地跑(CPU 可用),**写入路径零 LLM 调用**,数据不出机器
- 读取:智能全放这一端——查询分型路由 + BM25/向量 RRF 融合 + 日期锚定 + 读取时才生成摘要卡(永远可以用新模型重新生成,不冻结在旧模型认知里)
- 多租户/scoped token/多 agent 共享记忆胶囊都有

数据(同题同判据,脚本开源,复现约 $3.50 GPU 时):

- LongMemEval-S 检索 P@1:0.890(我们)vs 0.774(mem0 2.0.19 复现,同题同判据,各用默认嵌入)
- LongMemEval-S 端到端 500 题:42.6% → 75.4%(读取端路由的功劳;剔除 71 道判官故障题是 81.6%,双口径披露)
- 检索延迟 p95 0.34-0.80s(LLM controller 方案 26.9s)
- mem0 官方自报 94.4%,口径与我们不可比(harness/判官/被测模型都不同),不拉踩,说清楚就好

## 楼内 FAQ 预案(被问再回,不主动贴)

- **"自己测的自己赢?"** 复现脚本+判分协议+证据链全开源,$3.50 重跑;跑出来不一样欢迎发出来。
- **"数据隐私?"** 本地模式数据不出机器(嵌入也是本地 CPU);托管模式 token scoped 隔离,四条安全探针脚本开源,任何人可对生产端点重跑。
- **"BGE-m3 CPU 够吗?"** 单机够;写入只做一次嵌入,读取是检索不是推理,亚秒级。
- **"和 mem0/LangChain memory 的关系?"** 不是二选一。分型路由解决的是"找什么粒度",纯 RAG 只解决"找回来";欢迎把任何方案跑进我们的 harness 对比。
- **被挑刺判官公正性**:引判分卫生学——我们自己判官挂过 5 次、其中一次把 14.2% 的题静默记错,预注册协议+双口径披露就是为此设的。
