你的 AI 助手正在忘记你说过的话。不是偶尔忘,是系统性地忘。

ICLR 2025 有一篇 LongMemEval 论文,研究者干了件苦活:人工翻查 ChatGPT 的长对话记录。结论是,随着对话变长,你早先说过的关键信息——你的偏好、你的约束、你拍板过的决定——会被后面的内容**覆写掉**。你上周说的"我对花生过敏",三周后问它食谱,它推荐了宫保鸡丁。

【金句卡】
**AI 不是没有记忆,是把你的新话冲掉了你的旧话。**

## 为什么所有主流方案都在帮倒忙

业界的应对,归纳起来三条路:

**第一条,压缩。** 对话太长?写入时压成摘要。但信息在压缩那一刻就丢了——丢掉的偏偏经常是"未来某次提问恰好需要"的那句。

**第二条,提炼。** 用另一个模型把记忆整理成干净的知识卡片。看着清爽,但卡片的认知水平被**冻结在提炼那一天**。当初那个模型理解不了的关系,永远进不了你的记忆库。

**第三条,裸读。** 干脆把全部历史塞进上下文窗口。LongMemEval 的实测:长上下文直读,性能掉 30%-60%。

三条路,共享一个隐含假设:**写入的时候,就要决定什么值得记。**

【金句卡】
**写入时压缩,等于替未来的自己盲目下注——而赌桌对面站着你想象不到的提问。**

我们做了 130 天 agent 记忆系统后,把一个判断验证成了结论:写入的那一刻,你根本不可能知道未来会被问什么。今天觉得不重要而压掉的一句话,三个月后可能就是某次提问的唯一答案。

更拧巴的是成本结构:硬盘一年比一年便宜,模型调用永远那么贵。主流方案干的事,是把便宜的资源(存储)换成昂贵的资源(模型调用)。

## 我们把架构整个倒了过来

开源项目 nautilus-compass,核心只有一句话:

【金句卡】
**写入路径零 LLM 调用;全部智能,放在读取端。**

写入:你的观察原文逐字入库,只过一遍本地嵌入模型(BGE-m3,CPU 可跑,数据不出机器)。免费、无损、永远。

读取:来什么问题,走什么检索。问"用户的生活习惯"这种跨会话大问题,走总结卡;问"周二早上干嘛"这种具体事实,走原文块;带时间的,加日期锚定。向量召回接不住的精确标识符,BM25 词面检索兜住。这套读取端路由,在 LongMemEval-S 的 500 道题上,把端到端准确率从 42.6% 干到 **75.4%**。

顺便说下延迟:因为写入不调模型、读取只做检索,我们的检索延迟 p95 是 0.34-0.80 秒;而把 LLM 放在记忆主路上的方案,一次记忆操作要 26.9 秒。差了约 80 倍。这不是我们优化得好,是智能放对了时刻。

## 最想讲的一段:我们抓住了自己的判官 5 次

做这套系统绕不开评测,评测绕不开"让 LLM 给 LLM 打分"(LLM-as-judge)。这里有个行业级暗坑,值得每个做 AI 产品的人知道:

**判官挂掉的时候,不报错。**

它不会给你返回异常,只会安静地打出错误的分数。我们的判官被抓到过 5 次基础设施事故:环境变量名不对导致判分全 401、网关断连、预算被推理过程吃满……其中一次断连,把 14.2% 的题目**静默记成了错答**。也就是说,如果没有发现,我们的成绩单里有 14 个点纯属冤枉。

还有更细思极恐的:某次修复后,不同题型的分数一个涨 3.3 分,一个跌 1.9 分。如果只看总分,你会得出"修复没影响"的结论。

所以我们现在评测前先"预注册":判分标准、题目范围、过门条件,先白纸黑字写下来,再跑数;所有成绩双口径披露(75.4% 是全部 500 题,81.6% 是剔除 71 道判官故障题)。这套协议写成了论文,全在 GitHub 仓库里。

也借这里说破一个行业现象:mem0 官方自报 LongMemEval-S 94.4%,比我们的 75.4% 高——但这两个数字**不可比**:判官不同、被测模型不同、数据版本可能都不同。跨平台的裸分数比较,正是这个领域最大的噪音来源。能打的比较只有同题同判据:同样 500 题、同一把尺子、同样的嵌入模型,我们的检索命中率 P@1 0.890 对 mem0 复现版的 0.774。脚本开源,复现成本 $3.50,欢迎重跑。
