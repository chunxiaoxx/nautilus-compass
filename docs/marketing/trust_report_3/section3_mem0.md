# §3 mem0 三臂对照:一个开关,七分

> Trust Report #3 第三节。工件:BC1 三臂数据(docs/benchmarks/BC1_LAUNCH.md)+失败解剖;GitHub issue #7514(2026-10-01 发,双锚:先给数据后提问题)。

## 实验

30 题考试(考 AI agent 记得住自己的组织历史,题从 130 天真实轨迹出),同一 backbone,同一题,唯一变量=记忆路径:

| 臂 | 配置 | 得分 |
|---|---|---|
| 直连 | 结构化日志直读 | 16/18 |
| mem0 默认 | 写入时语义压缩 ON | **11/18** |
| mem0 关压缩 | 同上,唯一变量 infer 关 | **18/18** |

一个配置开关 = 7 分。全量工件公开(配置 diff/失败样本/逐题记录)。

## 失败解剖(不是猜,是抓)

失败集中在"机器可检字段"类题:mem0 写入时把结构化日志压缩成叙述句,`artifact: null` 这类字段在压缩中丢失——判分端按字段精确核对,字段没了就错。DIM3 复发识别 4/4 → 1/4 的塌点同因。

反超直连臂 2 分(18 vs 16)在单跑波动内,n=1 如实披露;核查确认无真值泄漏(raw 臂检索=原文片段)。

## 这不是 mem0 的 bug,是任务错配

写入压缩对对话式记忆是**正确设计**(token 省/检索自然)。错配在审计/取证场景:审计要的是字段级保真,压缩天然有损。所以我们的建议(已提给 mem0,issue #7514):文档里给合规/取证场景一个 `infer=False` 预设说明——一行文档救一类用户。

同函我们还问了一件更重要的事:他们 9/22 博客的 DolphinBench 对比评测(对 OpenAI Memory/LangMem/MemGPT),判分协议与数据未见公开——若公开,我们提供免费独立复算(判据冻结/全工件/失败样本逐条/共署,同 MemOS #2440 模式)。

## 与 §1 的呼应

我们对 mem0 的姿势和对我们自己的一样:**先给数据,再给修复建议,然后才提要求**。自家判分器开卷考试的丑事(§1)先公开,才有立场说"压缩丢字段不是缺陷是错配"。验证机构的双向纪律:被验证者会错,验证者自己也会错——我们只是把两边都摊开。

## 给读者的可行动结论

用记忆层跑审计/合规/取证负载:关写入压缩,或自测字段保真率。一个 20 分钟的三臂自测(我们的题和脚本开源)比任何 vendor 基准都贴近你的真实负载。
