# §1 我们的判分器先错了,然后我们修好了

> Trust Report #3 第一节成文(2026-10-01)。数字全部可溯源:runtime/judge_lora_p2v2/eval_report.json + docs/metering/P2_JUDGE_TRAINING_PREREG_20260930.md。

一家做"验证"的公司,最尴尬的死法是:自己的判分器不可靠。所以我们把这条线做成了公开案例——**从 66.2% 开始,把每一次翻车写下来。**

## 起点是一次差点发生的虚报

9/30,判分语料突破 500 条 labelled 的那天,我们准备宣布达标。复算时发现:语料里的 `is_correct` 字段不是独立真值,而是判分器自报结果的复写——"一致性 100%"只是同源复写。**如果当天宣布,就是一起自报事故。** 500 条退回 unlabelled,重走真值链(官方 answer + 机械规则判定)。

这不是孤例。同一天我们抓到第二个:第一版特征工程里,`sample_text` 包含了 `judge_output`——判分器输入里有被检者的旧答案,等于开卷考试。剔除后重跑,66.2%,离 85% 目标差 19 分。

第三个更微妙:M2 复算规则的子串匹配把 "five" 判为 "5" 的错误改写(等价表达被误伤)。机械规则有自己的边界,误伤也要入档。

## 修复:换架构,不换判据

66.2% 定谳为架构天花板(冻结向量模型+线性头≈语义匹配),目标 85% 需要 LoRA。10/1 凌晨,A100 训练 35 分钟:

- **配方**:Qwen3-1.7B + QLoRA(r16)+ verbalizer 三态——pass / fail / **insufficient_evidence**
- **三态是设计核心**:判分器没有把握时,输出不是硬猜,而是"证据不足"。U 态聚合起来就是待人工池——诚实的边界声明是特性,不是缺陷
- **纪律**:判据预注册在先(只许加严)/三折切分冻结 sha 防泄漏(同题跨 run 必同折)/test 集训练全程不可见

## 读数(三门全绿,原样)

| 判据 | 线 | 实测 | 判 |
|---|---|---|---|
| J1 test 二值准确率 | ≥85% | **88.51%** | ✅ |

热路径实测(另一台 A100 空档):单条延迟 P50=30ms/P95=42ms,批吞吐 118 条/秒——可以进实时链路,不用离线批处理。

全程工件:预注册档、训练日志全量、adapter、申报函(组织宪章要求算力使用申报),仓内可查。

## 这段故事对外说明什么

1. **验证公司的 credential 是"抓过自己"**。没有第二家 AI 公司会把"我们差点虚报""我们的判分器开卷考试"写进公开报告——这恰是它不可伪造的原因。
2. **U 态是信任的锚点**。85% 的判分器如果永远输出二值,错误的 15% 会伪装成正确;三态输出把不确定性显式化,下游可以决定"这批我不信,送人审"。
3. **数字的生产过程比数字本身值钱**。88.51% 不重要,重要的是它顶着预注册判据、防泄漏切分、不可见的 test 集——同样的框架可以复刻到任何厂商的基准复算,这正是我们对 mem0/MemOS/TypeSafe 提供的东西。
