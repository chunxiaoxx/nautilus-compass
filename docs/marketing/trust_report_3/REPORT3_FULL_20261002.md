# §1 我们的判分器先错了,然后我们修好了

> Trust Report #3 第一节成文(2026-10-01)。数字全部可溯源:runtime/judge_lora_p2v2/eval_report.json + docs/metering/P2_JUDGE_TRAINING_PREREG_20260930.md。

一家做"验证"的公司,最尴尬的死法是:自己的判分器不可靠。所以我们把这条线做成了公开案例——**从 66.2% 开始,把每一次翻车写下来。**

## 起点是一次差点发生的虚报

9/30,判分语料突破 500 条 labelled 的那天,我们准备宣布达标。复算时发现:语料里的 `is_correct` 字段不是独立真值,而是判分器自报结果的复写——"一致性 100%"只是同源复写。**如果当天宣布,就是一起自报事故。** 500 条退回 unlabelled,重走真值链(官方 answer + 机械规则判定)。

这不是孤例。同一天我们抓到第二个:第一版特征工程里,`sample_text` 包含了 `judge_output`——判分器输入里有被检者的旧答案,等于开卷考试。剔除后重跑,66.2%,离 85% 目标差 19 分。

第三个更微妙:M2 复算规则的子串匹配把 "five" 判为 "5" 的错误改写(等价表达被误伤)。机械规则有自己的边界,误伤也要入档。

## 修复:换架构,不换判据

66.2% 定谳为架构天花板(冻结向量模型+线性头≈语义匹配),目标 85% 需要 LoRA。10/1 凌晨,A100 训练 35 分钟:

- **配方**:Qwen3-1.7B + QLoRA(r16)+ verbalizer 三态——pass / fail / **insufficient_evidence**
- **三态是设计核心**:判分器没有把握时,输出不是硬猜,而是"证据不足"。U 态聚合起来就是待人工池——诚实的边界声明是特性,不是缺陷
- **纪律**:判据预注册在先(只许加严)/三折切分冻结 sha 防泄漏(同题跨 run 必同折)/test 集训练全程不可见

## 读数(三门全绿,原样)

| 判据 | 线 | 实测 | 判 |
|---|---|---|---|
| J1 test 二值准确率 | ≥85% | **88.51%** | ✅ |
| J2 校准误差 ECE(10桶) | ≤0.10 | **0.072** | ✅ |
| J7 vs 第一版 | ≥+10pt | **+22.3pt** | ✅ |
| J5 数据切分 sha | 冻结一致 | 三项全对 | ✅ |

热路径实测(另一台 A100 空档):单条延迟 P50=30ms/P95=42ms,批吞吐 118 条/秒——可以进实时链路,不用离线批处理。

全程工件:预注册档、训练日志全量、adapter、申报函(组织宪章要求算力使用申报),仓内可查。

## 这段故事对外说明什么

1. **验证公司的 credential 是"抓过自己"**。没有第二家 AI 公司会把"我们差点虚报""我们的判分器开卷考试"写进公开报告——这恰是它不可伪造的原因。
2. **U 态是信任的锚点**。85% 的判分器如果永远输出二值,错误的 15% 会伪装成正确;三态输出把不确定性显式化,下游可以决定"这批我不信,送人审"。
3. **数字的生产过程比数字本身值钱**。88.51% 不重要,重要的是它顶着预注册判据、防泄漏切分、不可见的 test 集——同样的框架可以复刻到任何厂商的基准复算,这正是我们对 mem0/MemOS/TypeSafe 提供的东西。

# §2 TypeSafe 四轮复算:一个 "(proof)" 的解剖

> Trust Report #3 第二节。所有发现来自 typesafe.ai 公开页面直抓(2026-09-26/30 两轮,HTML 直检),方法=calibration-claim-verify 流程;对外文本不指名(称 "an AI lab"),本报告仓内版保留坐标。

## 事情从一个点击开始

首页宣称 "193.6x Faster, 444.6x Cheaper — based on workflows for System One tasks **(proof)**"。"有 proof"——那我们点它。

**第一轮发现:点不开。** "(proof)" 是样式文本,不是链接:HTML 直检无 href,站内无 /benchmarks、无 methodology 页,/pricing 404。这不是我们抢先下结论——**是不可验证本身成为发现**。

**第二轮发现:同一页有两套数。** 页内 demo 微件可复算:$0.013880 → $0.000081 = **171x**,8.566s → 0.114s = **75x**。都是好数字——都不是 headline 的 444.6x/193.6x。同页双口径,无披露。

**第三轮发现:有一个声明是可验的。** "$42 per billion input tokens, 238x cheaper than [frontier model]"——42 × 238 ≈ $10/M,与公开牌价吻合。算术自洽。

**第四轮(结论):不是欺诈,是不可验证。** 两组倍数可能各自真实——对照集不同、口径不同、方法学不公开。买方无法在购买前复算任何一个 headline 数字。我们的定性:unverifiable(不可验证),不是 false(虚假)。

## 我们做了什么(动作留痕)

1. X 长文公开分析(2026-10-01,status/2105296550117458093)——只述事实,全部可溯源,不指名不推断动机
2. 邮件回应权(hello@typesafe.ai,官网一手邮箱):公开分析知会+完整回应邀请——**他们若有 methodology 文档,我们以同等可见度更正**
3. 免费独立复算 offer:判据冻结+全工件归档+失败样本逐条公开+报告共署+90 天挑战窗

## 这个案例对外说明什么

- **倍数的分母是商业决策,不是技术常数**。444.6x 对谁?哪个模型?什么任务分布?买得越贵,倍数越好看——"倍数-对照曲线"才是信息,单个倍数是营销
- **品类缺位**:整个 agent-memory/决策模型层(mem0/Zep/Letta 亦然,§4 详)运行在自报数字上。有资本、有叙事、有治理口号——没有一个可独立复算的数
- **验证机构的姿势**:先给回应权再公开(我们反过来了:公开后 24h 内补函回应权——次序教训已记),只述可复算事实,方法全公开

(对 TypeSafe 的复算 offer 仍在窗口内;若对方提供配置,我们将按预注册判据执行并全量公开工件。)

## 对照案例:当验证被接受时,会发生什么(gtaras7/typesafe-jev 全链)

> 澄清命名:gtaras7/typesafe-jev 是一个开源校准项目,与 §2 主体 typesafe.ai(商业公司)**无任何关联**,同名纯属巧合。把它放在这里,是因为它恰好是 §2 反面的正面版:**同样面对外部验证,一方关上门,一方把门打开——两种结局摆在一起,品类缺位的代价才具体。**(对外版此段沿用匿名化惯例,仓内版保留全坐标。)

同一个 48 小时内,这条链走完了验证机构能走的最远路径:

1. **送测请求**。对方在公开 issue 提问:Jev 在他们 CV 筛选任务上校准如何,并主动给了 5 个手标决定当"答案钥匙"。

3. **交付**。40/40 零错,agreement 92.6%(25/27),Brier 0.069,ECE 0.138,签名 mini-report,48h 承诺当天兑现。

5. **当日勘误**。我们没有辩解:在冻结的语料上独立复现他的证伪数字(18 行军事 0 女性/22 行非军事 16 女性/4 个 IT CV 全女性,精确匹配)之后才撤回;错误定位在叙事层(数据三层全干净,复算记录 9 项全绿);顺带披露一个对方没要求的信息(Brier 0.069 是弃权计错的从严口径,弃权重算≈0.046)。

**这段对照说明什么**:验证机构卖的不是读数,是协议;被测方的信用不是来自"数字好看",而是来自**接受审查并在被抓错时按程序认错**。我们自己的叙事层错误被抓住、当日勘误、全链留档——这件事对信任的贡献,大于 92.6% 本身。§2 的 TypeSafe 缺的不是 proof 链接,是这个循环。

# §3 mem0 三臂对照:一个开关,七分

> Trust Report #3 第三节。工件:BC1 三臂数据(docs/benchmarks/BC1_LAUNCH.md)+失败解剖;GitHub issue #7514(2026-10-01 发,双锚:先给数据后提问题)。

## 实验

30 题考试(考 AI agent 记得住自己的组织历史,题从 130 天真实轨迹出),同一 backbone,同一题,唯一变量=记忆路径:

| 臂 | 配置 | 得分 |
|---|---|---|
| 直连 | 结构化日志直读 | 16/18 |
| mem0 默认 | 写入时语义压缩 ON | **11/18** |
| mem0 关压缩 | 同上,唯一变量 infer 关 | **18/18** |

一个配置开关 = 7 分。全量工件公开(配置 diff/失败样本/逐题记录)。

## 失败解剖(不是猜,是抓)

失败集中在"机器可检字段"类题:mem0 写入时把结构化日志压缩成叙述句,`artifact: null` 这类字段在压缩中丢失——判分端按字段精确核对,字段没了就错。DIM3 复发识别 4/4 → 1/4 的塌点同因。

反超直连臂 2 分(18 vs 16)在单跑波动内,n=1 如实披露;核查确认无真值泄漏(raw 臂检索=原文片段)。

## 这不是 mem0 的 bug,是任务错配

写入压缩对对话式记忆是**正确设计**(token 省/检索自然)。错配在审计/取证场景:审计要的是字段级保真,压缩天然有损。所以我们的建议(已提给 mem0,issue #7514):文档里给合规/取证场景一个 `infer=False` 预设说明——一行文档救一类用户。

同函我们还问了一件更重要的事:他们 9/22 博客的 DolphinBench 对比评测(对 OpenAI Memory/LangMem/MemGPT),判分协议与数据未见公开——若公开,我们提供免费独立复算(判据冻结/全工件/失败样本逐条/共署,同 MemOS #2440 模式)。

## 与 §1 的呼应

我们对 mem0 的姿势和对我们自己的一样:**先给数据,再给修复建议,然后才提要求**。自家判分器开卷考试的丑事(§1)先公开,才有立场说"压缩丢字段不是缺陷是错配"。验证机构的双向纪律:被验证者会错,验证者自己也会错——我们只是把两边都摊开。

## 给读者的可行动结论

用记忆层跑审计/合规/取证负载:关写入压缩,或自测字段保真率。一个 20 分钟的三臂自测(我们的题和脚本开源)比任何 vendor 基准都贴近你的真实负载。
