## 一、开业日(对外服务)暴露的问题

### 1.1 陌生人照 README 验签 → INVALID

**伤口**:公开墙 15 张签名回执,3 张对入库字节验签失败两个月(11/23 才发现并修复)。README 首页那条"一条命令验证"是招揽用户的第一个入口——它对 Linux/Mac 新克隆返回 INVALID。
**根因**:签名对着含 CRLF 的 Windows 工作区字节做出;入库时换行被规范化成 LF。签名绑定的是字节,换行变了签名就废。
**已修**:✅ 原始字节入库+签名原件未动+CI 门(`test_wall_receipts_verify.py` 每次提交按入库字节逐张验签)。
**下一步**:发版把 CI 门带出去。

### 1.2 外部安全研究者报告漏洞 → 18 天未修

**伤口**:Nagizaaz Shaik 11/5 经 Gmail 报告 v14 recall 无鉴权+ingest_obs 路径逃逸。修复 11/19 就写好了,但从未提交、从未部署,报告人的确认回信也只发了"已收到"。
**根因**:修复写好了躺在 Mac 工作区里,没人提交;没有"安全修复必须 48h 内部署"的纪律;外部报告没有进值守轮的巡检面。
**当前**:✅ 修复已入库+临时缓解已部署(监听改 127.0.0.1,内网暴露归零);◐ 鉴权版待调用方迁移后部署。
**下一步**:① 调用方迁移(给 stop_hook/cloud_ingest 签发服务 JWT+配 COMPASS_V14_PROJECT_MAP);② 部署;③ 给报告人发"已修复"状态;④ GitHub issue #66 同步。

### 1.3 触客 8+3 家 → 0 转化

**伤口**:GitHub 触客 8 家首批+3 家二批+6 条独立复算邀请,全部零回应。dev.to 两篇新文 0 评论。唯一有来有回的是 a2a-x402#198(同行,非客户)。
**根因**:① 我们讲"独立验证"但自己墙上挂着坏签;② 触客话术讲的是我们能做什么,没讲对方能得到什么;③ 没有可让对方"30 秒体验"的入口——验签命令需要克隆整个仓。
**建议**:
- **v3.4.0 加入"网页端一命令验签"**:`nautilus.social/verify` 接受粘贴的 scorecard+sig+pubkey,网页端执行验签——不用克隆,不用装 Python,打开浏览器就能验。这是判读机构的**最低可信入口**。
- 触客话术从"我们能判分"改为"你的基准分数经得起独立复算吗?30 秒验一下"。

### 1.4 README 宣传已被内部定谳撤回的数字

**伤口**:README 仍在宣传"NACRE judge 1.7B LoRA 88.5% 三态"和"Judgment-fuel corpus 2,257 条"。而 10/19 用户亲审定谳:自产语料自举线从底层设计无效,语料量数字从一切对外叙事撤下。同一个判官在自产记录上 58/58 全 pass、空输入 28.9% 判 pass。HF 模型卡上没有任何勘误。
**已修**:🔶 事实清单和进化评审已写清;README/HF 卡**尚未修改**。
**下一步**:v3.4.0 之前必须完成——README 改为带适用域的表述(不是删掉,是标注"在官方真值集上 88.5%;在自产记录上无过滤力,详见 errata");HF 模型卡加勘误段;`/assay/criteria` 502 修复。

## 二、迁移日(Mac mini 迁移)暴露的问题

### 2.1 处方开了没人执行(14 次复发,至今未解)

**伤口**:10/19 开出 M1-M3 根治机制,11/12、11/17、11/23 三次复核仍红。处方不进执行者队列,没有回执协议,没有超期升级。COOR D_1104 整份任务单没进 Mac compass 的工作队列——Mac 在同期忙着修 MCP 和磁盘,根本不知道有这份单。
**根因**:处方写在 NAS 上,执行者的注意力在 Mac 上的 rounds.log/queue.md。两个世界没有交叉。
**建议**:v3.4.0 加 `处方→执行→回执` 闭环:处方投进平台信箱(不是 NAS 文件),值守轮扫到即入队列,完成后回执。已有 `submit_platform_task` / `ingest_platform_task_result` 两个 MCP 工具——**代码已存在,只是没有用它来管理自己的处方**。

### 2.2 验证工具自身撒谎(8 类、14 起)

**伤口**:打包脚本把半包哈希写进清单;robocopy 静默漏拷;空映射表计为交付✅;"已全部镜像"实为 1289 个空壳;TG 探针掐断长轮询造假阴性;PR 机审器 21/21 假"冲突";CI 读数过期;带宽归因错到影响了架构决策……**其中三行是审计席自己**。
**根因**:探针只测"能不能跑通",不测"报错了能不能报红"。一个永远返回绿的探针和没有探针一样——甚至更糟,因为它给人安全感。
**建议**:v3.5.0 加 `探针有效性分级`:
- L1 端口/进程(已普遍有);
- L2 业务语义(发一个已知坏的输入,看它报不报红);
- L3 金标对照(对已知样本集跑,判词全同向即警报——已给机审器装了一条,应做成 assay 通用件)。
这是 compass"独立验证"向内用的第一课:**先证明自己的探针能报红,再信它报的绿**。

### 2.3 通道/常驻件静默死亡(9 起)

**伤口**:值守 loop 断供 3 天只有日志一行小字;Tailscale 停 2 天全组织 MCP 瘫;launchd 装了不跑;tg 轮询静默死;模型名不存在三轮零产出;金丝雀已建但只覆盖智谱直连。
**已修**:🔶 金丝雀探针已上线(30 min 一探,连续 2 败即报警)。但只探 Mac 的通道;笔记本的 MCP 稳定性没有探针;中转站路径没有探针。
**建议**:v3.4.0 把金丝雀从"Mac 单机探针"升级为**多端探针网格**(Mac/笔记本/cloud 各一个,互相探测,任一端失联另一端能报)。

### 2.4 配置被外部改写(3 起)

**伤口**:`.claude.json` 的外部修改被存活对话框退出时回写覆盖——11/17 修的 MCP 配置被回滚,所有对话框继续显示"记忆服务无效"数天。
**根因**:Claude Code 进程持有配置文件快照,退出时整文件回写。
**已修**:✅ 防回滚脚本(`fix_compass_mcp.ps1`,须在关窗期执行)。
**建议**:长期看,MCP 配置不应放 `.claude.json`(单文件被多进程竞争写);应走 `~/.claude/mcp.json` 或环境变量。这属于 Claude Code 上游设计,我们能做的是把防回滚脚本做成计划任务(检测到回滚即自动修复)。

### 2.5 上下文爆炸(6 起)

**伤口**:全局 rules 107KB 固定注入致 25 会话/48h thrashing;值守轮单次工具结果 633KB;函件全文嵌首条 prompt。
**已修**:🔶 rules 下沉到 12 份 38KB;thrash 从 25→1。
**遗留**:T2 药方(函件摘要化 ≤2KB)从未执行——因为大行的来源其实是全局注入层(CLAUDE.md/ORG_BRIEF 的 instructions 附件),不是函件本身。
**建议**:v3.5.0 把 ORG_BRIEF 从"全局注入"改为"按需召回"——org brief 进记忆库,recall 命中时才展开。这能把每次注入的常量开销从 ~6KB 降到 0。

## 三、实际工作中的经验教训

### 3.1 自举线定谳 → 燃料来源只剩三条路

**伤口**:10/19 用户亲审 50 题:"这些根本无法判断""从底层就是错误的无效的"。自产工作记录(轮次/commit/函件)自始不构成判例。数量棘轮 2257→4002 全部无效。
**启示**:进化环(记忆→燃料→裁决→蒸馏)的"燃料"环节断了。剩下的燃料来源只有:
- **外部评测题**(hindsight 评测已有先例:40.8% vs 56.6%,真跑出来的数);
- **真实外部委托**(判读免费换判例——北极星写的就是这个,至今为 0);
- **NACRE 本地执行器线**(须先裁定"9B 自产总结作训练目标"是否触 10/19 红线)。
**建议**:v3.4.0 优先做**网页端验签入口**——它是"真实外部委托"的最短路径:对方粘贴证据包→我们回回执→双方各留一份→这就是判例。

### 3.2 蒸馏管线:355 复核→7 候选→0 发布

**伤口**:蒸馏复核工作量大但产出为零——355 条里 hold 348、候选 7、发布 0。自产摘要过不了源文复核。
**根因**:蒸馏的目标(摘要)和验收标准(保留源文关键事实)之间的差距太大——模型摘要天然丢细节。
**建议**:v3.5.0 把蒸馏产物从"摘要"改为**"结构化提取"**:不要求保留全文语义,只要求提取"(决策, 理由, 结果, 坐标)"四元组。结构化提取的验收标准清晰得多——四元组每个字段都能机械验证(坐标存在、结果可查、理由非空)。

### 3.3 NACRE 三版定义漂移、边界未裁

**现状**:10/6 白皮书(判分原生判分模型)→ 10/6 夜 v1.5(六能力原生)→ 11/20(本地 agent 执行器)。后一版未引用前一版,未说明与 E-NACRE-1(−36.6pp)的关系。中文名"溯衡"10/6 被否、11/20 又用。11/20 全部工作(规格 2 份+脚本 8 个+数据)未入库(已由审计席保存)。
**待裁**:
- 选一版作为现行定义,其余标历史;
- "9B 自产总结作 SFT 训练目标"是否触 10/19 "自产记录不构成判例"红线;
- 燃料路径 A(冻结等外部题)/ B(小而净 8B 对照)自 10/19 候拍未决;
- 训练预检 blocked:数据集 20 条(需 ≥48),金标 14 条未批。

### 3.4 记忆信噪比:82% 是机器蒸馏产物

**伤口**:1451 张卡中 1198 张(82%)是机器蒸馏,fact_status 962/969 为 inferred。召回候选 76-90% 被噪声占。不带项目名的召回前四名全是空壳 ingest 条目(v5 洪水,已修)。
**建议**:v3.5.0 加**库级纯度指标**进巡检:每日体检时报告"人工卡/机器卡/ inferred 卡比例",纯度下降超阈值即黄灯。

## 六、2026-11-23 实战补遗:v14 调用方迁移当日新增七条

> 来源:本日鉴权部署+调用方迁移全程。用户已批准纳入。

1. **影子实例→跨机常驻体登记表**:Mac mini 上一个跑了三天的求焦常驻体(v5-brain2)不在任何人登记里,鉴权切换后持续 401 三天无人知道。特性:每台机器的常驻体(LaunchAgent/systemd/cron)集中登记(名称、宿主、调用目标、认证方式、负责人),部署边界变更前先对表迁移。
2. **三套超时互不知晓→检索响应带覆盖率语义**:调用方超时<网关超时<填充预算,失败被折叠成"慢"而非"部分结果"。特性:recall 响应明确披露 `projects_scanned`/覆盖率/是否部分结果(联合召回已实现,推广为通用语义);调用方按披露决定重试而非加大超时掩盖。
3. **自动产物无治理→旧卡滚出+日摘要消化**:单项目 5.5 万张机器卡把 60k 全局缓存挤爆,300s 填充预算只装得动 ~250 份。特性:旧卡按时间滚出检索池进归档层;摄入端生成日摘要卡替代流水账(与 3.2 结构化提取同构);检索池按项目配额,防单项目挤爆全局预算。
4. **9886 死端口→机器可读拓扑清单**:代码注释声称的拓扑(9876=GPU 隧道/9886=云 CPU)与实况(9876=云 CPU daemon、9886 无进程)相反,误诊过一次。特性:端口/服务/隧道目标生成机器可读清单,健康探针按清单核对,漂移即报。
5. **推送撞车/双写互踩**:本 session push 被拒一次(Mac 值守并发落库)、10/14 双写互踩前科。纪律:落库前先 pull --rebase;共享正本按段声明所有权,不改他人段落。
6. **探针必须自带阴性对照**:本 session 自写探针把 /proc/environ 键 decode 成 str 却用 bytes 查,报"四服务无凭据"假阴性;与"永远绿的探针"对称——红灯也要先证伪探针自身。纪律:探针上线前先用"已知有/已知无"样本各跑一遍。
7. **验收脚本随服务出厂**:本次 14 项验收脚本只在 job tmp 目录,下次部署还得重写。纪律:runbook 第④步的验收脚本与代码同仓入库,部署即跑。

**归属**:2+3 插 v3.5.0;1+4+7 随 v3.4.0;5+6 落 ops 纪律(不改代码)。
