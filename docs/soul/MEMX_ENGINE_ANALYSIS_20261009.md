# 引擎选型分析:XERJ 类项目能否作为我们的检索底座?(MEMX 附录 · R404)

> 用户问:XERJ 类开源项目能否考虑?魔改+JEV?GitHub 上其他类似项目?结论先行:**借模式、不换底座;魔改的正确形态=适配器贡献,不是重平台化。**

## 一、我们的护城河在哪(先定位)

检索引擎(BM25+dense+RRF)是**商品件**——谁都有,难度不在。我们的差异化在验证/治理层:fact_status 写入门、三态判读、证据链、判例棘轮、复算信用。**换引擎不动护城河,只搬家具**;而搬家成本=重写 ingest/recall/dedup/M5 三件套/J4 门/drift 全套接线+行为回归——高成本低差异收益。

## 二、XERJ 逐项评(我们有一手交互经验)

| 维度 | 实测/已知 | 判断 |
|---|---|---|
| 引擎能力 | Rust 单文件部署,BM25+server-side 语义召回,autoindex 文件/节分块带溯源定位 | 能力属实,rc.80 还上了校准层 |
| 许可 | Apache-2.0 | ✓ 可魔改 |
| 成熟度 | 早期快进(我们看着它 10/7 一天合并两 PR),org 声量小 | 早采用非 1.0 引擎=风险 |
| 关系 | 协作热:槽位/署名/捐赠三线全开 | 关系是资产,别用重平台化赌它 |

**可抄的三个模式(抄思想不抄代码)**:①autoindex 的**文件/节边界分块+源 span 定位**(优于我们现按条目整存);②release-notes **CI claim-check**(发布说明每条数字对树复核——我们的"自报"纪律可自动化);③hub 的 manifest+lane 制式(已学,捐赠包即产物)。

## 三、"魔改+JEV"的正确打开方式

不是"魔改 XERJ 当我们的底座",而是**把我们的验证层做成 XERJ 生态的插件**:
- 他们 hub 已开 agent-session-trajectories 槽位(捐赠 PR #1255 在飞)——关系通道现成;
- 形态:XERJ namespace 级"assay-verified"记忆模式——入库走我们的 fact_status 门+判例校验,召回结果带我们的三态标注;
- jev-trust(信任中间件)管 API 层,compass 判读管内容层——两位一体输出;
- **这是分发渠道**(借他们的装机量触达用户),不是底座更换。列 M1 后评估。

## 四、GitHub 同类项目盘点(底座视角)

| 项目 | 定位 | 对我们 |
|---|---|---|
| mem0/Letta/cognee/Zep/MemOS | 白盒记忆层 | **被测对象**(测量线),不是底座来源——我们刚在 LongMemEval-S 全量赢过 mem0 |
| graphiti(Zep OSS) | 时序知识图谱 | 图谱路线与我们黑盒路线不同,观察 |
| txtai/LlamaIndex-memory | 框架级 | 重框架,我们是薄层哲学,不合 |
| XERJ | Rust 记忆引擎 | 见上:供模式+插件渠道 |

## 五、行动结论

1. **底座不动**:BGE-M3+BM25 混合(自研薄层)+A100 嵌入——昨晚实测的问题(吞吐/覆盖)已由 A100+渐进设计解决,无引擎级痛点;
2. **抄三模式**:autoindex 分块溯源(进 MEMX 站1 改进单)/claim-check 自动化(测^{自报}纪律的执法件)/manifest 制式(已用);
3. **插件贡献列 M1 后**:"assay-verified memory"XERJ 适配器=分发实验,开业后按 first-customer 信号定优先级;
4. **同一原则适用于 embedder 对拍**:候选是模型不是引擎;引擎层"魔改冲动"每次都要过这条——护城河不在那。
