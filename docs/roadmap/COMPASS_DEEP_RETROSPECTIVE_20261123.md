# Compass 深度复盘：从记忆服务到组织连续性控制面

日期：2026-11-23

## 一句话判断

我们已经把多个局部故障修成了可复用的守卫，但还没有把这些守卫收敛成一条完整的组织连续性链路。

Compass 的下一阶段重点不是继续增加工具数量，而是让任何一次迁移、交接、压缩、验证和外部提交都能回答四个问题：

1. 谁在什么项目和任务上工作。
2. 当前使用的代码、模型、配置和输入是什么。
3. 哪些结果已经由谁独立复核。
4. 哪个消费者真正采用了结果。

## 一、深度回顾后的总图

### 过去真正发生的事情

我们经历了多次 agent、模型、平台、Mac、NAS、云主机和工作树切换。每次切换都暴露出类似模式：

- 文件已经搬过去，但任务身份没有一起搬过去。
- 服务端口还在监听，但语义查询已经卡死或走了错误 fallback。
- 本地测试通过，但平台 reward、正式提交和客户验收没有闭合。
- 模型生成了摘要，但来源、哈希和事实状态没有绑定。
- 聊天窗口显示活跃，但真实消费者没有读到结果。
- 旧的状态文件和新的运行状态并存，导致不同对话框各自拥有一份“当前事实”。

这些问题看起来分散，实际都属于同一类问题。系统没有把身份、状态、证据和消费者绑定在同一条记录里。

### 当前已经形成的能力

[实测]

- Compass 记忆入口、BGE 嵌入、MPS 重排、JWT 和项目边界已经有多个独立修复。
- 本地 9B 已经成为 Compass loop 的实际模型。
- 9B 工具运行时已有重复调用、禁止写入、证据闸和收尾器。
- 923 个旧 session 卡已经进入可逆归档清单。
- 355 条压缩候选已经完成一轮语义复核，343 条仍保持 hold。
- CodeSense R192 已有隔离候选和本地交叉测试。
- Flywheel、Platform、Core、Compass 的交接报告已经可以保留负结果和未验收状态。

[不可验]

- 组织级 MCP projection 仍受到 `catalog changed/read_only` 影响。
- 历史记忆是否真正提高了组织任务成功率，还没有新的消费者回放证据。
- 9B 压缩候选还没有形成可训练的独立 gold set。
- Flywheel 还没有真实可训练 episode。
- CodeSense 还没有新的成功提交和甲方质检回执。

## 二、反复失败的五个根因

### 1. 身份连续性不完整

用户、项目、任务、工作树、模型、权限和回执没有强制绑定。结果是同一个“当前任务”在不同对话框里可能指向不同项目、不同版本或不同外部对象。

修复方向是 `Context Capsule`。每次 recall、ingest、dispatch、交接和外发都必须带 project scope、task id、owner 和权限边界。缺失时只能输出 `not_computable`。

### 2. 状态连续性被聊天界面掩盖

active、idle、进程存活、端口监听、工具可调用和任务成功被混成了一个“在工作”的感觉。

实际需要分成四层：

- 服务状态
- 线程状态
- 任务状态
- 消费者状态

只有消费者真正读回结果，任务才有资格进入 close 状态。

### 3. 证据连续性在迁移时断裂

文件、模型和配置搬到新环境后，live source、CI head、运行 PID、输入哈希和消费者回执没有一起迁移。

结果是本地 HEAD、远端 HEAD、已加载代码和报告中的版本可能不同。

下一版必须有 `Release Manifest`，至少记录：

- source SHA
- live file SHA
- launchd 或服务配置
- PID
- 模型标识和哈希
- CI head SHA
- 验证回执
- 回滚文件

### 4. 因果连续性被自报和自评破坏

9B 压缩、自家判官、自家脚本和自家记忆库容易互相证明，产生“自己生成、自己评估、自己晋级”的闭环假象。

所以 9B 必须是 compression subject。验证器必须独立，输入要固定，模型哈希要固定，holdout 不能被运行器修改。失败、hold 和 not-computable 必须保留。

### 5. 消费者连续性没有成为硬门

我们有不少“写入成功”“召回成功”“测试通过”的记录，但缺少“下游使用后真的减少错误”的读回。

长期记忆的价值必须由消费者结果来证明。没有 readback，只能报告服务能力，不能报告组织能力。

## 三、对近期工作的重新判定

### Compass 本身

[实测] 最近的工作已经从“修复单点故障”转向“增加失败守卫”：

- 默认项目洪水排除，防止自动日志淹没正常项目。
- 本地 9B loop 切换，减少外部模型依赖。
- 工具调用重复保护，防止小模型循环调用。
- 只读写入硬闸，防止模型违反任务边界。
- 证据收尾器，防止步数耗尽后没有可读结论。
- 重排超时冷却，防止一次网络超时放大成 22 秒 CPU fallback。
- 旧 session 归档，降低历史噪声对召回的影响。

这些工作产生了实际工程效果。它们还没有自动产生长期记忆价值，因为任务成功、错误复发和消费者采用率还未形成稳定回放。

### 9B 和压缩验证

[实测] 当前本地 9B 值守 loop 已运行，语义复核批次也已经完成。

[实测] 压缩复核状态为：355/355 处理，5 条 legacy hold，343 条 hold，7 条 approved receipt candidate，0 条正式发布。

这说明门控正在工作。大量候选被 hold 不是流程失败，而是证据不足被保留下来。

当前真正的缺口是 gold set 和消费者回放。NACRE 只有 15/2/3 的数据规模，训练预检未通过，不能把当前运行轨迹直接升级为模型训练成果。

### 组织和跨对话协同

[实测] 五框同步报告已经能够明确区分：

- 本地技术通过
- 平台评测
- 正式提交
- 客户验收
- 商业确认

这是重要进步。

[不可验] 各个对话框仍然没有完全共享同一份实时身份、任务和消费者状态。组织级 projection 仍受 catalog changed/read_only 影响，跨框同步报告本身也不能替代实时读回。

### CodeSense 和 Flywheel

CodeSense 已经完成本地难度候选，但 R190 reward、T02 kit、正式提交和甲方验收仍未闭合。

Flywheel 已经完成准入测试和负结果保存，但 p1-3 权威 manifest 缺失，真实可训练 episode 仍为 0。

这两条线共同说明一个问题。技术管道可以先于业务准入完成，但业务准入没有成立时，不能把技术结果升级成客户结果或训练燃料。

## 四、长期记忆到底应该提供什么价值

### 第一层价值是连续交接

切换 Codex、Claude、平台、模型或 agent 后，新执行者能直接知道：

- 当前任务
- 当前边界
- 已完成动作
- 失败和限制
- 证据位置
- 下一动作

这会减少重复解释和迁移期间的空转。

### 第二层价值是减少重复错误

长期记忆真正有价值的单位不是一条摘要，而是一条经过验证的“情境—行动—结果—教训”记录。

它应该帮助组织避免：

- 再次使用错误模型名
- 再次混淆本地完成和平台完成
- 再次把 HTTP 200 当成语义成功
- 再次把旧状态当成当前状态
- 再次把失败样本误当作训练燃料

### 第三层价值是形成验证燃料

经过来源绑定和独立验证的记忆，可以进入：

- Assay 反例库
- JEV 校准集
- 组织迁移回归集
- 9B 的拒绝样本和 gold set
- 创新模型的 frozen split

未经验证的记忆只能作为检索候选，不能作为训练真值。

### 第四层价值是形成组织级可审计能力

对外合作时，组织可以提供：

- 来源
- 版本
- 判据
- 反例
- 回执
- 消费结果

这样长期记忆才可能支持独立复算和商业合作，而不是只提供内部叙事。

## 五、下一版应该怎样落地

### 阶段 A：连续性底座

先实现四个稳定对象：

```text
Context Capsule   身份、项目、任务、权限
Evidence Capsule  输入、版本、配置、输出、失败、哈希
Handoff Capsule   主线、边界、剩余问题、下一动作
Consumer Receipt  谁读取、采用、拒绝或纠偏
```

阶段 A 的验收是身份和证据可追溯。它不要求模型训练，也不要求自动发布。

### 阶段 B：有限批次压缩

- 9B 每 2 小时处理固定数量候选。
- 每批保存输入快照和模型哈希。
- 压缩结果进入 review 队列。
- 失败最多重试固定次数。
- quota、模型身份、hash 或 scope 异常时自动 hold。

阶段 B 的验收是批次可恢复、候选可复算、失败不丢失。

### 阶段 C：独立验证和回放

- 独立 verifier 每天复核 approved candidates。
- 每周运行压缩前、压缩后、无记忆三组任务回放。
- 统计事实保留、错误复发、延迟、成本和采用率。
- 只有回放改善成立，才扩大晋级比例。

阶段 C 的验收是记忆能减少真实任务错误。

### 阶段 D：模型训练

- 先完成 32/8/8 数据集。
- 非实现者审核 gold。
- 固定 frozen split。
- 9B 只提供压缩候选和拒绝样本。
- 训练后的模型必须通过 holdout、反例和回滚测试。

阶段 D 的验收是模型收益可独立复算，且没有把自评结果当真值。

## 六、下一阶段的真实优先级

### P0

1. 建立 Context Capsule 和 project/task scope。
2. 让组织级 projection 从 `catalog changed/read_only` 恢复到可实时读回。
3. 统一 local、live、delivered、accepted 四态。
4. 把 7 条 approved receipt candidate 逐条生成 VerifyPack 草案，不自动发布。

### P1

1. 补齐 32/8/8 gold、validation、test。
2. 增加消费者回放。
3. 把迁移失败、模型路由失败、静默 HTTP 成功和 storage fallback 加入 failure corpus。
4. 继续观察重排超时和 cooldown 统计。

### P2

1. 只在真实或授权的 Flywheel episode 上做训练实验。
2. 只在 CodeSense 首件获得用户审核后进行平台试跑。
3. 把通过验证的记忆接入创新模型实验。

## 七、最终复盘结论

我们已经从“记忆服务能不能运行”推进到“记忆候选能不能被来源绑定、独立验证和安全晋级”。

我们还没有完成从“工程能力”到“组织能力”的最后一步，因为消费者回放、组织级实时状态、真实训练燃料和外部业务验收仍未全部闭合。

下一阶段成功的标志，不是更多服务、更多摘要或更多对话框，而是以下事实同时成立：

- 任意任务都能追溯身份、版本、权限和输入。
- 任意记忆都能追溯源文件、判据、验证器和签名。
- 任意迁移都能恢复下一动作，而不是重新猜测上下文。
- 任意训练材料都能证明自己不是模型自造的真值。
- 任意长期记忆都能通过消费者回放证明它确实减少了错误。
