# Compass vNext：9B 压缩验证与组织长期记忆闭环

日期：2026-11-23

## 结论先行

本地 9B 应该持续参与压缩和验证流水线，但不应该以一个永不停机、自动发布记忆的黑盒进程运行。

正确形态是持续值守、分批执行、可暂停、可恢复、可回放。9B 负责压缩候选，独立验证器负责挑战候选，Compass 负责来源绑定和召回，Assay 负责回执，消费者复读决定是否真的有用。

## 为什么要持续，但不能不间断硬跑

持续运行有三个价值：

1. 新会话不会长期堆积，压缩候选能及时进入复核队列。
2. 验证反馈可以尽快发现重复错误、旧状态和错误记忆。
3. 组织可以持续获得可追溯的上下文，而不是每次迁移前临时整理历史。

无限硬跑会产生四类问题：

1. 9B 可能把自己的错误压缩反复写回，形成自引用。
2. 外部判官配额、模型版本或网络异常时，会把失败误写成正常结果。
3. 大量低价值旧会话会挤压新鲜且重要的记忆。
4. 没有暂停点时，发现判据错误也无法安全止损。

因此，运行策略应当是持续调度和有限批次。每一批都有输入快照、模型哈希、验证回执、失败原因和下一批指针。

## vNext 的六层闭环

### 1. 原始层

原始会话、任务函件、工具轨迹和外部回执只读保存。每个候选绑定：

- `source_id`
- `source_sha256`
- `project_scope`
- `task_id`
- `captured_at`
- `fact_status`

原始层不被压缩结果覆盖。

### 2. 9B 压缩层

9B 只做压缩 subject：

- 提取事实、时间、路径、失败和下一动作
- 保留不确定性和负结果
- 生成摘要、锚点和候选主题
- 不自行宣布验证通过
- 不直接写入生产记忆

结构化工具调用继续关闭思考模式，以保证 JSON 可解析和延迟可控。需要长文本语义审查时，单独走 thinking enabled 的语义入口。

### 3. 独立验证层

验证器不能与压缩 subject 完全同源。每个候选至少检查：

- 来源哈希是否匹配
- 关键数字、时间、路径和身份是否保留
- 是否把推断写成事实
- 是否抹掉失败和限制
- 是否把旧状态冒充当前状态
- 是否能从源文件复述关键锚点

验证输出采用三态：`pass`、`hold`、`not_computable`。缺少输入或权限时必须停在 `not_computable`。

### 4. Assay 回执层

通过验证的候选生成 VerifyPack。回执至少包含：

- 输入和输出哈希
- 模型标识和版本
- 验证器标识
- 判据版本
- 锚点覆盖
- 反例结果
- 签名和时间

没有回执的候选只能停留在 review 队列。

### 5. Compass 记忆层

只有通过来源和验证门的候选才进入生产召回索引。长期记忆要保留：

- 事实状态
- 适用项目和任务范围
- 产生时间和失效时间
- 来源和回执坐标
- 召回后的采用记录

旧历史继续保留在归档区，归档不代表删除，生产索引也不等于全部历史。

### 6. 消费者复读层

记忆是否有价值，要看下游是否正确使用。每次重要召回都应记录：

- 命中了什么
- 读取了哪个源文件
- 是否改变了下一步行动
- 是否避免了已知错误
- 是否产生新的验证或纠偏

没有消费者复读时，只能说“召回成功”，不能说“记忆有效”。

## 建议的调度方式

### 高频轮，每 30 分钟

- 9B 和 Compass 服务健康检查
- 新候选数量和队列积压
- 近期失败是否重复出现
- 重排超时率和 fallback 率
- 不做大批量压缩，不做自动发布

### 批次轮，每 2 小时

- 选择固定数量的新候选
- 运行 9B 压缩
- 写入不可发布的 review 队列
- 绑定 source hash 和模型 hash
- 失败可重试，重试次数有限

### 复核轮，每天一次

- 独立验证 approved candidate
- 抽查 hold 和 not_computable
- 运行事实保留和反例测试
- 形成 signed receipt

### 回放轮，每周一次

- 从真实任务中抽取固定问题
- 比较压缩前、压缩后和无记忆对照
- 统计任务成功率、错误复发率、延迟和成本
- 只有回放有效，才允许提高记忆晋级比例

## 必须设置的停止条件

出现以下任一情况，自动停止晋级，保留原始数据和失败回执：

- source hash 不匹配
- 验证器与 subject 使用同一未隔离输入
- 关键事实保留率低于门槛
- hold 比例突然异常下降，疑似判据失效
- 同一错误连续出现
- 外部模型身份、配额或版本无法确认
- 召回延迟超过预算
- 消费者复读缺失
- 组织项目范围或任务身份无法绑定

## 三阶段落地

### P0，先完成稳定闭环

目标是让系统稳定地产生候选和回执，不追求自动发布。

- 固化 `source_id + source_sha256 + project_scope`
- 将 355 条复核结果转成统一状态表
- 统一 `hold`、`not_computable`、`approved_receipt_candidate`
- 为每条 approved candidate 生成 VerifyPack 草案
- 保持生产记忆写入关闭

通过标准是候选状态可重放、失败可复查、任何候选都能找到来源。

### P1，验证长期记忆是否真正有用

- 建立 32/8/8 的独立 gold、validation、test 集
- 由非实现者审核 gold
- 运行压缩前后和无记忆对照
- 测事实保留、错误复发、时间新鲜度和召回延迟
- 先小范围发布，通过回放后再扩大

通过标准是记忆能够减少真实任务错误，并且没有明显增加错误记忆采用。

### P2，把验证结果用于创新模型

- 9B 继续作为压缩 subject
- 独立 verifier 产生训练标签和拒绝样本
- 固定 frozen split 和模型哈希
- 做 LoRA 或轻量头的隔离实验
- 以 holdout、反例、成本和回滚为共同门槛

通过标准是模型在未见任务上保持事实和验证能力，且收益可以被独立复算。

## 组织长期记忆能够带来的价值

### 对个人和对话框

- 不必反复解释项目背景、约束和过去失败
- 切换 Codex、Claude、平台和 agent 后能快速接上下一动作
- 让“当前状态”和“历史经验”分开，减少旧结论污染今天判断

### 对组织协同

- Compass、Platform、Agent、Flywheel 可以共享最小可信投影
- 交接不再依靠长篇聊天记录
- 每个任务都有 owner、边界、证据、剩余问题和下一动作
- 能追踪哪个团队真正消费了某条记忆

### 对质量和研发

- 把失败案例变成可复算的反例库
- 把重复踩坑变成自动检查
- 为 assay、JEV 和创新模型提供带来源的训练材料
- 让“压缩是否保真”和“验证是否独立”可以分别度量

### 对商业和外部合作

- 对外可以提供可验证的复算包和负结果
- 合作方能看到来源、判据、模型和回执
- 记忆服务的价值可以从“存了多少条”转成“减少了多少错误、节省了多少交接时间、提高了多少任务成功率”
