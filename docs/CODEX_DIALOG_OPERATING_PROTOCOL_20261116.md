# Codex 多对话框工作协议

版本：2026-11-16  
适用范围：Compass、nautilus-core、nautilus-v5、客户交付、移动端、外部沟通等对话框。

## 目的

让每个对话框都能独立推进一件清楚的工作，同时让用户随时知道：

1. 这个对话框负责什么；
2. 当前做到哪一步；
3. 证据在哪里；
4. 卡在哪里；
5. 下一步是谁来做。

共同原则：**智能 = 压缩 × 验证**。摘要不能代替原始证据，服务在线不能代替任务成功，自报完成不能代替外部回执。

## 对话框分工

| 对话框类型 | 负责 | 不负责 |
|---|---|---|
| Compass 主线 | 总目标、优先级、跨对话框协调、最终状态 | 代替所有专线执行细节 |
| 客户交付线 | 一个明确客户任务的预检、构建、评测、提交 | 处理其他任务或移动设备 |
| 记忆验证线 | 9B 压缩、语义复核、召回回放、历史吸收 | 修改客户任务结果 |
| 服务维护线 | daemon、模型通道、权限、探针、运行基线 | 把服务存活写成业务完成 |
| 外部沟通线 | Gmail/GitHub 读回、草稿、发送回执 | 未授权发送、替别人承诺 |

一个对话框只保留一个主要目标。需要并行时，必须先登记任务名、负责人、写入路径和停止条件。

## 每次开始时使用的短模板

```text
目标：本轮要完成的一件事
当前事实：[实测] 已知状态；[不可验] 尚未读到的状态
本轮只做：一个具体动作
完成判据：什么证据出现才算完成
输出格式：先给结论，再给证据、阻塞和下一步
```

如果这五行没有写清楚，不启动新的分支、不启动新的长任务。

## 每次结束时使用的短模板

```text
结论：完成 / 部分完成 / 失败 / 等待外部条件
已完成：最多 3 条
证据：文件、日志、回执或提交号
阻塞：具体错误和责任边界
下一步：一个动作、一个负责人、一个完成判据
```

默认汇报不超过 5 个要点。只有用户要求“展开”时，才输出完整过程。

## 什么时候开新对话框

不为每个小动作开新对话框。只有满足下面任一条件才新开：

- 需要真正并行且不会写同一批文件；
- 需要独立审查，避免执行者自己给自己打分；
- 需要 Git Worktree 隔离代码改动；
- 当前对话已经过长，需要先写交接再归档。

`side chat` 只用于审查或咨询；`fork` 只用于平行方案；Worktree 只用于隔离代码。完成后必须把结论写回主线交接，不在旁支里形成第二个事实版本。

## 证据和写入纪律

- 原始会话、原始日志、结果文件和模型输出保留在持久路径；摘要只作为索引。
- 每个外部任务至少记录任务号、命令、开始/结束时间、退出码、stdout/stderr、结果文件和哈希。
- 页面显示“处理中”不等于作业有结果；进程存在不等于服务可用；分数存在不等于客户验收。
- 外部发送、提交、部署和结算必须有当前任务授权，并保存消费者侧回执。
- 脏工作树只提交明确授权的文件，不能用全量 `git add .` 扫走其他对话框的改动。

## Compass 主线的固定节奏

1. 读当前状态和最近交接；不从旧摘要推断今天的状态。
2. 选择一个最高优先级且可验证的动作。
3. 执行或分派，不同时启动互相冲突的写入者。
4. 独立读回原始结果，保留失败和未验证状态。
5. 写回主线交接，给出下一动作。

主线只管理“做什么、为什么、做到哪、下一步”，不在一条消息里混入所有技术细节。

## 迁移和移动端使用方式

- CLI 负责长时间终端工作；桌面 Codex 负责查看线程、差异和审批；手机负责远程查看、短指令和审批。
- 需要跨设备继续时，使用同一个已保存线程和连接的桌面主机；不要在手机上另开一个同名线程。
- 本地任务、Cloud 任务和 Worktree 任务必须在交接里标明运行位置。
- 任务结束后先 `/recap`，必要时 `/compact`，确认交接文件写好后再 `/archive`。

## 一次性改进旧对话框的顺序

不要同时重写所有历史对话。按下面顺序逐个处理：

1. 列出对话框名称、项目目录、负责人和当前主线；
2. 选出一个主线程，其他重复线程只读审计；
3. 给主线程补“目标、判据、证据、下一步”四项；
4. 归档已经完成或重复的线程；
5. 只把尚未解决的阻塞和最新证据写回主线；
6. 下一轮再处理下一个对话框。

每次只改一个对话框，避免“整理工作”本身制造新的分叉。
